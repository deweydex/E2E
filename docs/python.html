How a click reaches a database and comes back

Start hereFrom click to row and back again

Press Buy on a vending machine page and the number of snacks left changes a moment later. That small change involves a browser, a network, a server program, a database and a file on a disk. This page follows one click through all of them, slows it down, and lets you build every stage yourself.

In this edition the server, the setup script and the database code are all written in Python. The page uses plain HTML and CSS plus one short script of about fifty lines of code. That script is JavaScript, because a browser can run only JavaScript, and it does one job: it asks the server for data and changes the screen to match.

Along the way we answer a set of questions that usually stay hidden. What does a database do that a file cannot? How does a program talk to a database? What is a server, and what does it mean to set up an API? What is JSON, and why does the page need it? How does something that arrives from a server end up changing the screen?

We explain each piece of code beside the code itself, including the reasons behind the choices we made. Some choices have alternatives that are just as good, and we point those out too.

Try it firstThe finished machine, running in your browser

What is real here, and what is simulated

A web page cannot open a network port, so no real server program is running, and that is why this is a simulation. Three real things are running, though. Pyodide is the Python interpreter compiled into a form that browsers can run, and it runs the real setup_db.py and the real data layer and route table from server.py, including real SQL on a real SQLite database. The page's own script, app.js, is the file you will read in Part 10, with no changes. A service worker, which is a script that sits between a page and the network, notices each request whose address starts with /api/, and hands it to Python instead of sending it anywhere.

The simulated part is the wire. No bytes travel between two programs, so Stations 3 and 9 of the journey are imitated, and the HTTP layer of the server is replaced by the short file below. That replacement is possible because we kept the layers apart, which is the reason for the design that Part 8 explains.

Part 1The journey of one click

Suppose you press Buy on slot A1. The screen changes after a few milliseconds, and we can split those milliseconds into twelve stations. The diagram shows them in order, and the list below it says what happens at each one.

  1. The browser notices the click.A click is an event, a message the browser creates whenever something happens on the page, such as a click, a key press or the page finishing its loading. Our script has asked the browser to run a function whenever a click lands inside the area that holds the slots.
  2. The script builds a request.The script calls fetch, a browser function that sends a request, which is a message to another program that says what we want and how we want it done. Here the message says, in effect, please buy one item from slot A1.
  3. The request travels.The message goes to an address made of a host (which computer) and a port (which program on that computer). On your own machine the browser and the server share one computer, so the message never leaves it, yet it follows the same rules as a message sent across the world.
  4. The server chooses a handler.The server is a program that waits for requests and answers them. It reads the message, compares the method and the path with a table of routes, and passes the request to the function responsible for that route. We call that function the handler.
  5. The handler checks the input.Validation means testing that what arrived is well formed before we use it. Slot ids look like A1 or B2, and anything else is turned away with an explanation.
  6. The handler sends SQL to the database.SQL (Structured Query Language) is the language we use to ask a relational database to find or change rows. The handler sends it through a connection, an open line of communication between a program and a database.
  7. The database changes the row.The database applies the change as a transaction, a group of steps that either all happen or none happen. Then it reports how many rows it changed.
  8. The handler packages the result.Inside the server the result is a Python dictionary. A network carries only bytes, so the handler converts the result into JSON (JavaScript Object Notation), a text format for structured data. Turning structured data into text is called serialising it.
  9. The server sends a response.The response has three parts: a status code that says how things went (200 means success), headers that describe the message, and a body that holds the JSON.
  10. The reply reaches the script.Waiting for a network reply takes time, so fetch gives back a promise, an object that stands for a value that has not arrived yet. When the reply arrives the promise settles, and our script carries on from the line where it waited.
  11. The script changes the DOM.The DOM (Document Object Model) is the browser's live tree of objects, one for every element on the page. The script edits the tree: new text, a changed class, a disabled button.
  12. The browser repaints the screen.The browser notices that the tree has changed, works out the new layout and redraws. We write no code for this step, and it is the reason an edit to the DOM becomes visible.

You do not need to memorise the list. Each later part zooms in on a few stations, and the code explanations carry matching badges so that you can find your place again. If you only remember one thing from this part, remember that the browser and the server are two separate programs that cooperate by exchanging messages, and that the database sits behind the server, never in front of it.

Part 2Why a database at all

What a page and a server forget

Reload a page and every variable in its script disappears. The server forgets in the same way. If it kept the stock count in a variable, stopping the program would reset the count, and two copies of the server would disagree about it. Something outside both programs has to keep the count safe between visits, and it has to keep exactly one shared count, even when many people press Buy at the same moment.

A text file could store the numbers. Think about what you would need to add to make that file behave. You would want a way to find one row without reading the whole file, a rule that stops two programs from writing at once and ruining each other's work, a promise that a half finished change is undone if the power fails, and a rule that stock can never drop below zero. A database management system is a program that has already solved those problems, and a relational database keeps its data in tables of rows and columns.

Five things a database gives us

Persistence. The data survives when the programs stop. Structure. A schema declares the tables, the columns and the type of each column, so every row has the same shape. Queries. SQL lets us ask for exactly the rows we want, and the database finds them quickly, using an index when one exists. Safe changes. Transactions make a group of changes all-or-nothing, and they keep simultaneous users from tripping over each other. Rules. Constraints such as NOT NULL and CHECK (stock >= 0) make the database itself refuse bad data, even if a bug in our code tries to write it.

Our vending machine needs one table. It has a primary key, slot_id, which is a column whose value is different in every row and so identifies exactly one row.

slot_iditem_nameprice_centsstock
A1Sparkling Water1758
A2Salted Peanuts1255
B1Chocolate Bar2003
B2Oat Biscuits1500

Why the price is a whole number of cents

You might expect a column called price holding 1.75. Computers store numbers with fractions in binary, and many decimal fractions cannot be written exactly in binary. In most languages 0.1 + 0.2 gives 0.30000000000000004. A shop that adds up prices with numbers like that will eventually be wrong by a cent. Whole numbers are exact, so we store 175 cents and convert to euros only at the last moment, when we display the price.

Where SQLite fits

SQLite is a database engine that lives inside a library that our program loads. It keeps everything in one ordinary file, and it needs no installation and no separate server. Larger systems such as PostgreSQL and MySQL run as their own server programs and accept connections from other programs. All of them speak SQL, and they all have connections, transactions and constraints, so what you learn here carries over. We choose SQLite for the same reason a driving lesson starts in a quiet car park: it removes everything that is not the lesson.

Part 3Why the browser cannot reach the database

A fair question follows from Part 2. If the page needs data from the database, why can the page not ask the database itself? Why do we put a server in the middle?

There are two answers, a practical one and a more important one. The practical answer is that a browser has no way to open a database. SQLite is a file on the server's disk, and bigger databases listen for a specialised protocol on a port that should never face the public internet.

The more important answer concerns trust. The visitor owns the browser. They can read every line of the page, edit it, run any script in the developer console, or skip the page altogether and send requests by hand from a terminal. Anything we ship to the browser is readable, and any check that happens only in the browser can be skipped. So the rules of the vending machine cannot live there. They live on the server, where the visitor cannot reach them, and the server is the only program that holds a route to the database.

Look at how the Buy request in this project is designed. The browser names a slot and nothing else. It does not say what the price is, how many items to take, or which SQL to run. Those decisions belong to the server.

A prediction to make first

Imagine that the page sent { "slot": "A1", "price_cents": 0 } with every purchase and the server trusted it. What would a curious visitor do with the developer console? Then think about which other parts of our design would protect us even if the server were careless, and which would not.

Part 4Servers, ports and HTTP

Clients, servers, hosts and ports

A client is a program that starts a conversation, and a server is a program that waits for conversations to start. The word server also names the computer that runs such a program, but in this tutorial it always means the program. Our browser is the client, and our Python program is the server.

To reach a server, a client needs an address. The host says which computer. We use 127.0.0.1, a special address that always means this computer, and the name localhost means the same thing. A computer can run many servers at once, so the port, a number between 0 and 65535, tells the operating system which waiting program should receive the message. We pick port 8000. Together, the scheme, host, port and path make a URL:

http://127.0.0.1:8000/api/slots/A1/buy

HTTP, the agreement between them

A protocol is an agreement about the order and shape of messages, and HTTP (HyperText Transfer Protocol) is the agreement that browsers and web servers use. Every exchange has two messages, a request and a response, and both are plain text with a fixed layout. We captured a real exchange from the running project, and we can read it piece by piece.

Status codes

The status code is a three digit number that tells the client how things went before it reads a single byte of the body. The first digit gives the family: 2 means success, 4 means the client made a mistake, and 5 means the server did. We use five codes.

CodeNameWhen we send it
200OKThe request worked and the body holds the result.
400Bad RequestThe client sent something we cannot make sense of, such as the slot id hello.
404Not FoundThe request was well formed, yet nothing exists at that address, such as slot Z9.
409ConflictThe request was fine, but it clashes with the current state of things. Buying from a sold-out slot is a conflict.
500Internal Server ErrorSomething broke inside the server. The fault is ours and not the client's.

Methods, and a server with no memory

We use two methods. GET asks the server to read something and promises to change nothing. POST asks the server to do something, and the server is allowed to change data when it does. HTTP is also stateless, which means the server treats every request as a fresh conversation and keeps no memory of the previous one. The state of our machine, the stock count, therefore lives in the database and never in a variable inside the server.

Part 5What an API is, and what setting one up means

The word API stands for Application Programming Interface. An interface is the part of a program that other programs are allowed to use, and it describes what you may ask for and what you will get back, without saying anything about how the answer is produced. A web API offers that interface over HTTP, and it usually replies with JSON, because JSON is easy for programs to read.

Setting up an API therefore means making four decisions and then writing code that keeps the promises those decisions make.

The first decision is which things the API offers. Each thing gets a URL. Ours are the collection of all slots, /api/slots, and each single slot, /api/slots/A1. An address like this is often called an endpoint.

The second decision is which actions are allowed on each thing. The method says which action. Reading uses GET, and buying uses POST.

The third decision is the shape of the data in both directions. The contract says which fields exist and what type each one has.

The fourth decision is how outcomes are reported. We use status codes for the category and a JSON message for the detail.

MethodURLWhat it doesOn successOn failure
GET/api/slotsLists every slot200 with a JSON array of slotsNone expected
GET/api/slots/A1Shows one slot200 with one slot400 for a malformed id, 404 for a missing slot
POST/api/slots/A1/buyBuys one item from the slot200 with the updated slot400, 404, and 409 when the slot is sold out

The two shapes of JSON that cross the network are a slot and an error:

A slot, followed by an error

{
  "slot_id": "A1",
  "item_name": "Sparkling Water",
  "price_cents": 175,
  "stock": 7
}

{ "error": "Oat Biscuits is sold out." }

The contract matters because the page and the server are written at different times, and possibly by different people. If the server renames stock to quantity, the page breaks, and nothing in the browser will warn anyone beforehand. That is why the contract is worth writing down, even if only as a table like the one above.

Why buying uses POST

A method is safe when calling it changes nothing, and GET is meant to be safe. Browsers, link previews in chat apps and search engine crawlers all send GET requests freely, and they may repeat them. If buying were a GET, a chat app that previews a link could buy a snack. Buying is also not idempotent, which means that doing it twice does not leave the same result as doing it once: two presses buy two snacks. Reading is idempotent, and that is why it is safe to refresh a page as often as you like.

REST, in one paragraph

Many web APIs follow a style called REST (Representational State Transfer). In this style, URLs name things with nouns, the method chooses the action, and each request is complete in itself. Our API borrows that style without trying to follow every rule of it. The route table in the server file is the API written down as code, and in Part 8 you will see that the table is only a few lines long.

Part 6The same data in five shapes

The same fact, that slot A1 has seven items left, takes five different shapes on its way from the disk to the screen. Following the shapes explains a great deal about why the code looks the way it does.

1. A row in the database

slot_id | item_name       | price_cents | stock
A1      | Sparkling Water | 175         | 7
↓ fetchone() returns a row, and dict(row) converts it

2. A Python dictionary in the server

{'slot_id': 'A1', 'item_name': 'Sparkling Water', 'price_cents': 175, 'stock': 7}
↓ json.dumps(...) serialises the dictionary into text

3. Text on the network (JSON)

{"slot_id": "A1", "item_name": "Sparkling Water", "price_cents": 175, "stock": 7}
↓ response.json() parses the text into an object

4. An object in the browser's script

{ slot_id: "A1", item_name: "Sparkling Water", price_cents: 175, stock: 7 }
↓ createSlotCard copies the values into elements with textContent

5. Elements in the DOM

<p class="stock">7 left</p>

Only the third shape can cross the network, because a network carries bytes and the others are structures inside the memory of one program. Serialising turns a structure into text, as in the step from shape 2 to shape 3. Parsing turns text back into a structure, as in the step from shape 3 to shape 4. Every arrow in the pipeline is a place where something can go wrong. A key can be missing, a number can arrive as text, or a value can be empty, and we will meet each of those problems in the code.

A prediction to make first

The fourth and fifth shapes both live in the browser. Why might we bother with the fourth at all, instead of writing the JSON text straight into the page?

Part 8Build 2: the server and its API

The server is the longest file, and it has a layered design. The data layer talks to the database and knows nothing about HTTP. The route layer connects URLs to data functions and checks input. The HTTP layer reads requests and writes responses, and the last lines start the server. Each layer uses only the one beneath it, so we can change one without disturbing the others. The file lists the layers in that order, and the explanations follow the same order.

You start the server with python server.py and visit http://127.0.0.1:8000/api/slots. The browser shows a line of JSON. You have just used the API with no page and no script involved, and the terminal printed one log line for your request.

Part 9Build 3: the page, in HTML and CSS

The page has two files and no logic. The HTML describes what exists, and the CSS describes how it looks. Before we read them, one idea needs a name. When a browser loads an HTML file it builds the DOM (Document Object Model), a tree of objects with one object for each element. The screen shows a drawing of that tree, and a script can change the tree. Changing the tree is how a server's answer reaches the screen.

Part 10Build 4: the script that connects it all

The script has one job: it asks the server for data, and it changes the page to match what the server says. A browser can run only JavaScript, so this part of the project is JavaScript, and it stays short on purpose. Everything with rules in it, such as the stock count and the validation, lives in the Python server.

A prediction to make first

When you press Buy, the script sends one request and gets one reply. Before you read Part 11, try to describe in your own words what the browser would show if the reply were slow, say five seconds. What does the visitor see during those five seconds, and how could we improve it?

Part 11Running it and watching the traffic

Now we run the whole thing and look at the traffic. You start the project with these commands in a terminal, inside the project folder:

Watching the traffic in the browser

Using the API without the page

The page is only one client of the API. Another client is the address bar. If you visit http://127.0.0.1:8000/api/slots you see the raw JSON, with no page at all. A third client is a command line tool called curl:

Three requests from a terminal

curl http://127.0.0.1:8000/api/slots
curl -i http://127.0.0.1:8000/api/slots/B2
curl -i -X POST http://127.0.0.1:8000/api/slots/A1/buy

The -i option shows the response headers, and -X POST chooses the method. In older versions of Windows PowerShell, curl is an alias for a different command, so you may need to type curl.exe. A phone app would be a fourth client, and none of these clients would need any change on the server. That independence is the point of having an API.

Part 12Breaking it on purpose

A system teaches you most when it fails in front of you. Each experiment below breaks something in a controlled way. Try to predict the outcome before you run it, and then compare your prediction with the explanation that follows. After each experiment you can reset the machine by running the setup script again.

You can open vending.db in the free program DB Browser for SQLite, or use the sqlite3 command line tool if it is installed. Python 3.12 and newer also offers python -m sqlite3 vending.db.

Experiment 1: three kinds of sold out

In the page, press Buy on the Chocolate Bar until it is sold out. The button greys out after the third press. Now send the same purchase from a terminal, where no disabled button can stop you: curl -i -X POST http://127.0.0.1:8000/api/slots/B1/buy. Finally, try to break the rule inside the database itself, by running UPDATE inventory SET stock = -1 WHERE slot_id = 'A1'; in your SQLite tool.

What happened, and why

The terminal request returns 409 Conflict with a message, so the server refused even though the page had been bypassed. The SQL statement fails with CHECK constraint failed: stock >= 0, so the database refused even though the server had been bypassed. We now have three layers with three jobs. The disabled button is a courtesy to the visitor, the server holds the rule and explains it kindly, and the database is the last line of defence.

Experiment 2: two kinds of wrong address

Visit http://127.0.0.1:8000/api/slots/hello and then http://127.0.0.1:8000/api/slots/Z9. Notice which status code each one returns before you read the next paragraph.

What happened, and why

The first returns 400 and the second returns 404. The word hello is not shaped like a slot id, so the client made a mistake in how it asked. The id Z9 has the right shape, but no such slot exists, so the question was fine and the answer is nothing here. Splitting those two cases lets a client tell a typing mistake from a missing item.

Experiment 3: joining strings versus passing parameters

Run python injection_demo.py. The script looks up a slot twice, once with a normal id and once with the text x' OR '1'='1, and it does so with two different methods of building the query. The output looks like this:

Output

The user typed: A1
Joined into the string:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = 'A1'
  rows returned: 1
Passed as a parameter:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = ? with value 'A1'
  rows returned: 1

The user typed: x' OR '1'='1
Joined into the string:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = 'x' OR '1'='1'
  rows returned: 4
Passed as a parameter:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = ? with value "x' OR '1'='1"
  rows returned: 0
What happened, and why

When the query is built by joining strings, the text typed by the user becomes part of the SQL itself, and the condition OR '1'='1' is true for every row, so all four rows come back. This attack is called SQL injection. When the value travels as a parameter, the database receives the SQL and the value separately, and so the value can only ever be data. It matches no slot id and returns nothing. Some drivers also allow several statements in one call, and in those the same flaw lets an attacker delete a table. That is why every query in this project uses a ? placeholder, even when the value comes from our own validated code.

Experiment 4: opening the page straight from disk

Double-click public/index.html in your file manager so that the browser opens it from disk, with the server still running. The page stays on Loading.... Open the developer console and read the errors.

What happened, and why

The console reports that it cannot load file:///app.js. In the HTML we wrote /app.js, and a path that starts with a slash means from the root of whatever served this page. Our server is that root when it serves the page, but from a file the root is the top of your disk. Two lessons follow. A page and its API need a server that delivers both, and links that start with a slash behave differently depending on where the page is hosted. A project site on GitHub Pages lives under a path such as /project-name/, so a link that starts with a slash would point at the wrong place there, and relative links such as app.js would work.

Experiment 5: the page on one port and the API on another

Leave the API running on port 8000. In a second terminal, serve only the public folder on port 9000 with any static file server, for example python -m http.server 9000 --directory public --bind 127.0.0.1 (or npx http-server public -p 9000 if you prefer Node). In the page's script, change the two URLs that begin with /api/ so that they begin with http://127.0.0.1:8000/api/. Then open http://127.0.0.1:9000.

The page says Cannot reach the server. Is it running?, yet the server is running. Check the console and check the server's terminal before you read on.

What happened, and why

The console says the request was blocked by CORS policy, and the terminal shows that the server received the request and answered it normally. The browser delivered the request, then refused to let the script read the answer. The reason is the same-origin policy. An origin is the combination of scheme, host and port, and 127.0.0.1:9000 is a different origin from 127.0.0.1:8000. By default a script may read responses only from its own origin, which stops a malicious page from reading your private data out of another site you are signed in to. A server can opt in with a header, and the policy it opts in to is called CORS (Cross-Origin Resource Sharing).

To fix it, add one header to every response: self.send_header("Access-Control-Allow-Origin", "http://127.0.0.1:9000") inside send_body, next to the other headers. Restart the server and reload. The page now works, and the Buy button works too. Requests that carry a JSON body or custom headers trigger an extra preliminary check, an OPTIONS request, which a server would then have to answer as well. We chose the exact origin for the header and not *, which means any website. That wildcard is acceptable for public data, and it is risky when the response depends on who is asking.

Experiment 6: stopping the server

Stop the server with Ctrl+C, return to the page that is served from it, and press Buy. Look at the status line and at the console.

What happened, and why

The page shows Cannot reach the server. Is it running? and the console reports a refused connection. That is the same message that Experiment 5 produced, even though the cause was different. fetch rejects its promise whenever no usable response arrives, whether the server is down, the network is off or the browser blocked the answer. A response that arrives with a 404 or a 409 counts as an answer, and fetch does not treat it as a failure. You might think about how the script could give the visitor a more accurate message, and whether it can know enough to do so.

Experiment 7: changing data without touching any code

With the server running, change a price with UPDATE inventory SET price_cents = 99 WHERE slot_id = 'A1'; in your SQLite tool, and then reload the page.

What happened, and why

The price of Sparkling Water becomes €0.99. Neither the server nor the page was edited or restarted. The database is the single source of truth, and every request reads it again. That is why we keep data in a database and logic in code.

Part 13The choices we made, and the alternatives

Almost every line in this project was a choice, and most choices had a respectable alternative. The table lists the main ones, with the reason we chose as we did and the situation in which you would choose differently. When you build your own project, a useful habit is to ask the same two questions about each decision.

The choiceWhy it fits hereWhen you might choose differently
SQLite for storageNothing to install, one file to copy, and the same SQL that bigger systems use.When many programs or many computers write at once, or when you need accounts, backups and monitoring at scale, a server database such as PostgreSQL fits better.
The Python standard library for the server, not a frameworkEvery mechanism stays visible: reading the request, routing and writing the response. Nothing needs installing.In real projects, because a framework such as FastAPI or Flask supplies routing, validation, safe static files and a production server. The next section shows the same API in FastAPI.
A new database connection for each requestThe server handles each request in its own thread, and a SQLite connection belongs to the thread that made it. Opening a SQLite connection is very cheap.With a client-server database, opening a connection is slow, so servers keep a pool of connections and lend them out.
The same server delivers the page and the APIBoth share one origin, so no CORS settings are needed, and there is only one program to start.When the page lives on a static host such as GitHub Pages and the API lives elsewhere, the origins differ, and the API must send CORS headers and be reachable over HTTPS.
JSON replies, with the page building its own elementsThe page and the API stay independent, and the same API can serve a phone app or another program.When a page must work without scripts, the server can send finished HTML instead. A form and a full page reload then replace the script.
Prices stored as whole centsWhole numbers are exact, so sums never drift.Some databases offer an exact decimal type, and you can use that. A floating point column for money is never a good choice.
POST for buyingBuying changes data and is not idempotent, so it must not be something that a link preview can trigger.Other changes may use other methods. Many APIs use PUT to replace something, PATCH to adjust part of it and DELETE to remove it.
Parameterised queries everywhereThe database receives SQL and values separately, so a value can never turn into SQL.There is no good reason to choose differently.
One UPDATE with AND stock > 0A single statement checks and changes together. Reading first and writing afterwards leaves a gap in which two simultaneous buyers could both take the last item.When a purchase needs several steps, group them in one explicit transaction, and think about what the database does when two transactions collide.
Rules in three placesThe page offers convenience, the server holds the rules and explains them, and the database is the last line of defence.You may drop the check in the page, because a visitor can skip it anyway. The checks in the server and the database stay.
textContent rather than innerHTMLtextContent treats a value as plain text. innerHTML parses it as markup, so an item name that contained a script tag could run code in every visitor's browser. That attack is called cross-site scripting (XSS).innerHTML is acceptable for markup that you wrote yourself and never for data that came from somewhere else.
A <template> element for the cardThe structure of a card stays in HTML, where it is easy to read and to restyle, instead of hiding inside strings in the script.Front end frameworks such as React and Svelte generate this part for you, and they become worthwhile as pages grow.
Redrawing the card from the server's replyThe page shows what the server says, so it cannot drift away from the truth. If somebody else bought the last item a second ago, the reply says so.An optimistic update shows the change first and corrects it if the server disagrees. It feels faster on a slow network and costs more code.
A fixed list of files that the server will sendA server that sent whatever file the URL named could be asked for the server's own source code or for the database file itself. That attack is called path traversal.A framework's static file helper handles this safely, and you should use it instead of writing your own.

Where frameworks fit

In a real project you would rarely write the plumbing of a server by hand. A framework provides routing, input validation, safe static file serving, error handling and a production-ready server, and it lets you write only the parts that are particular to your application. We built the plumbing ourselves so that each mechanism is visible once. To see the difference, here is the same API in FastAPI, a popular Python framework. It is optional, and it is included in the download as server_fastapi.py.

You run it with pip install fastapi uvicorn and then uvicorn server_fastapi:app --port 8000. FastAPI also writes documentation for your API automatically. Visit http://127.0.0.1:8000/docs and you find the endpoints that we described by hand in Part 5, laid out in a standard format called OpenAPI that other tools can read.

Part 14Extending it yourself

When the project works, you can grow it. Each of these extensions is small and exercises a different idea from this page. They are written as problems for you to approach in your own way, and the hints say where to start and no more.

  1. A restock route. Add POST /api/slots/A1/restock with a JSON body such as {"amount": 5}. The route must reject a missing body, a body that is not valid JSON, and an amount that is not a whole number from 1 to 100, and each rejection should be a 400. To read a body you can use int(self.headers["Content-Length"]) to learn how many bytes to read, then self.rfile.read(n) to read them, and json.loads to parse them.
  2. A sales log in the same transaction. Create a sales table with an id, a slot id that references inventory, a timestamp and the price paid. Make a purchase insert a sale row and decrement the stock inside one transaction. Why should the sale store the price again instead of looking it up later? Then prove that the transaction works: raise an error between the two statements and check that the stock did not change.
  3. A summary route. Add GET /api/sales/summary that returns, for each item, how many were sold and how much money they earned. This needs a JOIN and a GROUP BY, so it is a good place to practise SQL where the result has to arrive as clean JSON.
  4. Automatic refresh. Make the page ask for the list of slots every five seconds with setInterval, and open the page in two windows. When you buy in one window, how long until the other window notices? Polling like this is the most direct approach, and techniques such as server-sent events and WebSockets let the server push changes to the page instead.
  5. Separate hosting. Serve the page from its own port and make it work properly with CORS, as in Experiment 5. Then think about what you would change to host only the page on GitHub Pages while the API runs somewhere else. You would need an absolute API address, a CORS header for the origin of your Pages site, and an API reachable over HTTPS, because a page served over HTTPS may not call an insecure address.

ReferenceGlossary

The terms below appear in this tutorial, in alphabetical order. Each entry names the part where the term is first explained in detail.

API
Application Programming Interface. The agreed ways one program may ask another to do things. (Part 5)
Body
The data that follows the headers in a request or a response, such as the JSON of a slot. (Part 4)
Client
A program that starts a conversation with a server. Our browser is the client. (Part 4)
Connection
An open line of communication between a program and a database. (Part 1)
Constraint
A rule that the database enforces on its own, such as NOT NULL or CHECK (stock >= 0). (Part 2)
Contract
The agreed shape of requests and replies in an API: which fields exist and what type each has. (Part 5)
CORS
Cross-Origin Resource Sharing. Headers with which a server allows a page from another origin to read its responses. (Part 12)
Database management system
A program that stores data safely and answers queries about it, for example SQLite or PostgreSQL. (Part 2)
DOM
Document Object Model. The browser's live tree of objects, one for every element on the page. (Part 1)
Endpoint
One address of an API, such as /api/slots/A1. (Part 5)
Event
A message that the browser creates when something happens on the page, such as a click. (Part 1)
Event delegation
Listening for events on a parent element instead of on each child, which also covers children added later. (Part 10)
fetch
The browser function that sends an HTTP request from a script and returns a promise. (Part 10)
Handler
The function that answers one kind of request. (Part 1)
Header
A name and value that describe a request or a response, such as Content-Type. (Part 4)
Host
The name or number that says which computer a request goes to. (Part 4)
HTTP
HyperText Transfer Protocol. The agreed text format of requests and responses between browsers and servers. (Part 4)
Idempotent
Describes an action that leaves the same result whether you do it once or many times. (Part 5)
JSON
JavaScript Object Notation. A text format for structured data, used by most web APIs. (Part 1)
Method
The word in a request that says what kind of action is wanted, such as GET or POST. (Part 4)
Origin
The combination of scheme, host and port. Pages may read responses only from their own origin unless the server allows more. (Part 12)
Parameterised query
A query in which values travel separately from the SQL text, marked by placeholders such as ?. (Part 12)
Parsing
Turning text into a structure that a program can use, such as JSON text into an object. (Part 6)
Path
The part of a URL after the port, such as /api/slots. (Part 4)
Path traversal
An attack that uses parts such as /../ in a URL to reach files that were never meant to be served. (Part 13)
Port
A number that tells the operating system which waiting program should receive a message. (Part 4)
Primary key
A column whose value is different in every row, so it identifies exactly one row. (Part 2)
Promise
An object that stands for a value that has not arrived yet. (Part 1)
Protocol
An agreement about the order and shape of messages. (Part 4)
Relational database
A database that keeps its data in tables of rows and columns. (Part 2)
Request
A message from a client that says what it wants. (Part 1)
Response
The message a server sends back, made of a status code, headers and a body. (Part 1)
REST
Representational State Transfer. A style of web API in which URLs name things and methods choose the action. (Part 5)
Route
A pairing of a method and a path pattern with the function that handles it. (Part 1)
Safe method
A method that changes nothing on the server, such as GET. (Part 5)
Same-origin policy
The browser rule that stops a page from reading responses that come from another origin. (Part 12)
Schema
The declared structure of a database: its tables, columns and types. (Part 2)
Serialising
Turning a structure in memory into text or bytes so that it can be stored or sent. (Part 6)
Server
A program that waits for requests and answers them. (Part 1)
SQL
Structured Query Language. The language for asking a relational database to find or change rows. (Part 1)
SQL injection
An attack in which text typed by a user becomes part of an SQL statement. (Part 12)
Stateless
Describes a server that treats every request as new and remembers nothing between them. (Part 4)
Status code
The three digit number at the start of a response that says how the request went. (Part 4)
Transaction
A group of database steps that either all happen or none happen. (Part 1)
URL
Uniform Resource Locator. The address of something on the web, made of scheme, host, port and path. (Part 4)
Validation
Testing that input is well formed before using it. (Part 1)
XSS
Cross-site scripting. An attack that gets a page to run a script that arrived as data. (Part 13)
