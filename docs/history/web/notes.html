Introduction

From the Browser: how the web learned to respond

This history follows the web from its first page in 1991 to the browser you are using today. It looks at four parts that every website is made of, asks what each part does and when it arrived, and follows how its jobs changed over thirty years.

Four parts, four jobs, four colours

Every website is built from the same four parts. Each one has a colour, and each section of these notes carries a tag in that colour for every part it is about. Each tag also carries its name, so nobody has to rely on colour alone.

HTML is the structure. It says what each part of the page is: a heading, a list, a link.
CSS is the look. It sets colours, fonts, spacing and layout.
Scripts are the behaviour. JavaScript runs in the visitor's browser and changes the page.
Server is the computer that sends the page, runs programs and keeps the data.

Over thirty years, jobs moved between these four parts. A job that needed a script in 2000 might need only a line of CSS today. That movement is the story.

The history runs in seven chapters. They overlap a little in time, because the four parts changed at different speeds: chapter 4 starts in 2009, before chapter 3 ends.

Before we start: history is messy

The dates in these notes mark when something appeared or became a standard. They do not mark when everyone used it. Every technology here spread at its own speed, overlapped with older ones for years, and depended on others that came before it.

How a new technology spreads

In 1962 the sociologist Everett Rogers described how new ideas spread through a group of people in his book Diffusion of Innovations. He sorted people into five groups by when they take up something new.

GroupShareWho they are
Innovators2.5%Try something while it is still rough and risky
Early adopters13.5%Take it up once it shows promise, and others watch them
Early majority34%Wait until it works reliably
Late majority34%Join once most people already use it
Laggards16%Switch last, often only when the old way stops working

The bell curve shows how many people adopt in each period. Add them up, and the total so far follows an S-curve: slow at first, then steep, then flat. The percentages are idealised, and real technologies rarely follow the shape exactly.

Chapter 1 · 1991 to 1995: Documents and forms

This chapter in the other formats: the slides · the era page

The web begins as pages of text and links, and forms let readers write back.

The first page was text and links HTML Server

Tim Berners-Lee put the first web page online at CERN, the physics laboratory near Geneva, in 1991. The page held only text and links. It could not respond to anything except a click on a link, and each click asked the server for a whole new page. That first page is still online at info.cern.ch.

Each request brings back one whole page, and every website still starts this way.

Forms let readers write back HTML Server

Forms became part of HTML 2.0 in 1995. A form turns a page from something you read into something you can answer, and it works in three steps.

  1. A visitor fills in a form on an HTML page and presses Send.
  2. A program on the server reads what they typed. Early programs used a system called CGI, the Common Gateway Interface.
  3. The program builds a brand new page as its answer and sends it back.

Here the server becomes more than a file cabinet, because it now runs a program. The cost is in step 3. Every answer, even "please fill in your email", meant a trip to the server and a whole new page. Scripts arrived partly to fix that.

How fast did it spread?

In 1995 fewer than 1 person in 100 worldwide was online. The first pages were written for a tiny audience that grew every year.

Chapter 2 · 1995 to 2004: Scripts, styles and server languages

This chapter in the other formats: the slides · the era page

Browsers and servers both learn to run programs, and plugins fill the gaps.

Scripts and CSS arrive within a year Scripts CSS

JavaScript, 1995. The Netscape browser added a language that runs inside the page. For the first time, a page could change without asking the server.

CSS, 1996. Style sheets moved colours and fonts out of the HTML. Browsers supported CSS unevenly for years, so many sites kept using tables and scripts for layout and effects.

Through the early 2000s, scripts did jobs that CSS and HTML do today: changing a picture when the pointer moved over it, opening and closing panels, checking forms and opening pop-up windows. Chapter 7 shows those jobs moving back.

Servers learn to build pages from data Server

PHP was first released in 1995. A PHP file looks like HTML with small pieces of code inside. The server runs that code, fills in the gaps from a database, and sends plain HTML to the browser.

On the server

<p>Hello, <?php echo $name; ?></p>

What the browser receives

<p>Hello, Aoife</p>
Language or toolWhat it was
PHP, 1995Code mixed into the page itself
ASP, 1996Microsoft's version of the same idea
WordPress, 2003A publishing system written in PHP, still behind a large share of sites
Ruby on Rails, 2004, and Django, 2005Frameworks for Ruby and Python

A common setup was called LAMP: Linux, Apache, MySQL and PHP. Each request runs the PHP again, so the same file can show a different page to every visitor. WordPress still works this way: when someone saves a post, PHP stores it in a database and builds the page from it each time someone visits. The browser never sees PHP. It only ever receives the HTML that the server built.

Plugins filled the gaps Plugins HTML

A plugin is a program added to the browser to do what HTML could not. Flash was the best known. For over a decade it played video, animation and games on the web.

  • 2007. The first iPhone arrives without Flash.
  • 2014. HTML5 adds <video> and <audio>, so a page can play a clip on its own.
  • 2020. Flash reaches its official end in December.

Plugins are not one of the four parts, so their tag is grey. The lesson of Flash is that a feature built into HTML outlasts one added from outside. Plugins were also a frequent security risk, which helped speed their end.

Web 1.0: a few people wrote, and many people read HTML Server

Looking back, people now call the web of roughly 1991 to 2004 Web 1.0. It had four features.

  • Pages were mostly fixed documents, like a brochure.
  • Most visitors could read, but not add anything.
  • Layout was built from tables, and style was written into tags such as <font>.
  • Most changes still meant loading a whole new page from the server.

How fast did it spread?

Netscape lost three-quarters of its share in three years. The scripts and server languages of this chapter took far longer to become near-universal, and the survey data that shows it starts only in 2015.

Chapter 3 · 2005 to 2014: Web 2.0, HTML5 and every screen

This chapter in the other formats: the slides · the era page

Pages update without reloading, visitors write into the web, and HTML and CSS take on new jobs.

Ajax: update one part, not the whole page Scripts Server

With Ajax, a script asks the server for a little data in the background and changes one part of the page, while the rest stays still. Gmail in 2004 and Google Maps in 2005 made the idea famous.

Today the script uses fetch, and the data usually travels as JSON, a plain text format for lists and records.

jQuery smooths over browser differences Scripts

In the 2000s each browser ran JavaScript a little differently. John Resig released jQuery in 2006. It gave one short way to write a script, and that script worked in every browser.

With jQuery, from 2006

$("#menu").slideToggle();
$.ajax({ url: "/news" });

Built into every browser now

document.querySelector("#menu");
fetch("/news");

Browsers now agree with each other, and they copied the best of jQuery's ideas. New sites rarely need it, but many older sites still use it.

Visitors start writing into the web Scripts Server

From about 2004, the web changed in who made it. Tim O'Reilly's 2005 essay made a name for this change popular: Web 2.0. Four ideas mark it out.

IdeaWhat it meansLeans on
Comments and reviewsAnyone can add to a page, and the server stores it.Server
Social networksThe people are the content.Server
WikisMany people write one page together.Server
Pages that updateAjax keeps the page fresh without reloading.Scripts

Web 2.0 is less a technology than a change in who makes the web. Its tools were scripts, servers and databases working together. Wikipedia (2001) and Facebook (2004) are useful examples. A good answer to "what changed with Web 2.0?" names a difference and gives an example of each side.

One page, every screen CSS

Phones made fixed-width pages hard to read. In 2010 Ethan Marcotte named the answer responsive web design: one page whose layout changes to fit its screen. It rests on three things: flexible layouts, flexible images and CSS media queries.

.cards { display: grid; grid-template-columns: 1fr 1fr 1fr; }
@media (max-width: 600px) {
  .cards { grid-template-columns: 1fr; }
}

The same HTML sits behind both screens, and only the CSS changes. A non-responsive page keeps one fixed layout, so a phone must zoom or scroll sideways. Two older alternatives also existed: an adaptive site switches between a few fixed layouts, and a separate mobile site serves different pages, often at an address beginning with m.

HTML5 gives HTML new jobs HTML

HTML5 became a finished standard in 2014. It added new tags and retired old ones whose jobs had moved to CSS.

What it added:

  • Semantic tags: <header>, <nav>, <main>, <article>, <footer>
  • <video> and <audio>, in place of plugins
  • Form rules: required, type="email", pattern
  • <canvas>, for drawing with a script
DeprecatedUse instead
<font>CSS font and color
<center>CSS text-align
<frame>CSS layout
<big>CSS font-size

A semantic tag says what its content is. Screen readers, search engines and the next person who edits the page all depend on that. Each retired tag described how text looked, and that job moved to CSS. A deprecated tag may still work in a browser, but it is no longer part of the standard, and a validator flags it.

CSS versions: from three levels to many modules CSS

VersionYearWhat it brought
CSS11996Fonts, colours, margins and spacing
CSS21998Positioning, :hover, and styles for print
CSS3from about 2011Split into modules: media queries, transitions, animations, flexbox, grid
Nowno CSS4Each module grows on its own. :has() and container queries arrived in 2023.

After CSS2, CSS stopped having single numbered versions. It became a set of modules, each with its own level. "CSS3" now means modern CSS in general, and each feature arrives when every major browser supports it.

Broadband reached half of US adults by 2007. Smartphones went from a third to nine in ten in about a decade, and by 2017 half of all web visits came from a phone.

Chapter 4 · 2009 to now: Scripts grow up

This chapter in the other formats: the slides · the era page

JavaScript moves onto the server, frameworks build whole pages, and TypeScript adds types.

JavaScript moves onto the server Scripts Server

Ryan Dahl released Node.js in 2009. Node runs JavaScript outside the browser, so a developer can write the page's scripts and the server's program in one language. Its package registry, npm, lets developers share small pieces of code with each other.

Until 2009, the server side of this picture would have been PHP, Java, Python or Ruby. Now the same language can run at both ends.

Frameworks build whole pages in the browser Scripts

A framework builds the page from data inside the browser, and updates only the parts that change. A site built this way is called a single-page app, because the browser loads one page and the script does the rest.

FrameworkYearFrom
AngularJS2010Google
React2013Facebook
Vue2014Evan You

Frameworks suit big applications such as email or maps, where the page changes all the time. The cost is a large script to download before anything appears, which makes them heavy for a brochure site or a blog. Many sites now send ready-made HTML first, and add scripts only where they help.

TypeScript adds types to JavaScript Scripts

Microsoft released TypeScript in 2012. A type says what kind of value something holds, such as a number or a piece of text. TypeScript checks the code against its types before it runs, then turns it into plain JavaScript for the browser.

function priceWithVat(price: number): number {
  return price * 1.23;
}

priceWithVat("ten");   // stopped here: "ten" is text, not a number

The browser still only runs JavaScript. TypeScript helps the person writing the code, and it matters most on big projects with many people, where a wrong kind of value can travel a long way before anything breaks.

How fast did it spread?

JavaScript in the page was already near 100 per cent. On the server, and as TypeScript, it rose slowly over years.

Chapter 5 · 2016 to 2022: The platform catches up

This chapter in the other formats: the slides · the era page

CSS gets real layout, every site gets a padlock, web apps work offline, and the browsers finally agree. Few of these changes made headlines, but together they are why building a site today is so different from 2014.

The server sends HTML first again Server Scripts

The single-page apps of chapter 4 were slow to show anything. The answer was to go back to the oldest pattern on the web: the server sends a whole, finished page.

  • Server rendering. Next.js, released in 2016, builds a React page on the server, so the browser gets HTML it can show straight away.
  • Static site generators. Tools such as Hugo build every page once, ahead of time, and a host like GitHub Pages sends the files as they are.
  • Scripts where they help. The page arrives ready to read, and scripts wake up only the parts that need them.

View source on a single-page app

<div id="root"></div>
<script src="app.js"></script>

View source on a page rendered by the server

<h1>Timeline</h1>
<ul><li>1991: the first page</li>…</ul>

This closes a loop. Chapter 1 began with a server sending whole pages, chapter 4 moved the work into the browser, and from 2016 the work moved back to the server with modern tools.

CSS Grid: real layout at last CSS

In March 2017, Chrome, Firefox and Safari all shipped CSS Grid within a few weeks of each other. For the first time, CSS could lay out rows and columns together. Twenty years of tables, floats and workarounds came to an end.

.page {
  display: grid;
  grid-template-columns: 1fr 2fr;
  grid-template-areas:
    "header header"
    "nav    main"
    "footer footer";
}

Pages in 1996 and 2001 used tables for exactly this layout. Grid does the same job in CSS, so the HTML can stay semantic.

Web pages start to behave like apps Scripts

Progressive web apps. A service worker is a script that sits between the page and the network. It can keep copies of files, so the site still opens offline. Add a small manifest file, and a phone lets you install the site on its home screen like an app. The term was coined in 2015, and Safari added service workers in 2018. Squoosh, an image tool that works offline, is an example.

WebAssembly, 2017. By November 2017 every major browser could run WebAssembly. It lets code written in languages such as C, C++ and Rust run inside a page at close to full speed. Figma, a design tool, runs in the browser this way.

Both changes made the browser a place to run real applications, not just show documents.

Every site gets a padlock Server

HTTPS encrypts everything between the browser and the server, so nobody on the same Wi-Fi can read or change it on the way.

  • December 2015. Let's Encrypt starts giving out free certificates, so any site can use HTTPS.
  • July 2018. Chrome begins marking every plain HTTP page as "Not secure".

Before free certificates, HTTPS cost money and effort, so mainly banks and shops used it. Many newer browser features, including service workers, only work on HTTPS pages, and most hosts now give every site HTTPS for free.

Cookie banners and dark mode Server CSS

GDPR, May 2018. The EU's data protection law began to apply on 25 May 2018. Sites that track visitors must ask first, and refusing has to be as easy as agreeing. The cookie banner became part of almost every page. This change came from a law, and it touches the server, which stores visitor data.

Dark mode, 2019. Phones and laptops gained a dark setting, and CSS gained a way to follow it. One media query lets a page pick its colours to match the device. This change came from operating systems, and it touches CSS.

@media (prefers-color-scheme: dark) {
  body { background: #111; color: #eee; }
}

HTML stopped having version numbers HTML

In 2019 the W3C and the WHATWG, the two groups that had each published an HTML standard, agreed to keep one: the HTML Living Standard. HTML now grows a feature at a time, and a feature counts once every major browser supports it. "HTML5" was the last numbered version, and people still use the name for modern HTML in general. Many of the jobs that scripts did in 2005 are now done by HTML and CSS alone; chapter 7 shows which.

The browsers finally agree HTML CSS Scripts

Internet Explorer retires. Microsoft retired Internet Explorer on 15 June 2022. For years, sites had carried extra code just to work in it.

Interop. Also in 2022, Apple, Google, Microsoft and Mozilla, with Bocoup and Igalia, launched Interop 2022, a yearly project to make the same features work the same way in every browser. Its public dashboard at wpt.fyi shows how well each browser scores.

The browser wars of chapter 2 made jQuery necessary. Interop is why the new HTML features in chapter 7 now arrive in every browser at about the same time.

How fast did it spread?

HTTPS and Flexbox climbed fast once browsers supported them. Grid, everywhere from 2017, was on only 12 per cent of pages by 2022, and Flash faded slowly for a decade.

Chapter 6 · 2023 to now: AI and the web

This chapter in the other formats: the slides · the era page

Machines start to write web pages, read them, summarise them and use them. This chapter differs from the others, because nobody knows yet how it ends, so it closes with questions instead of a verdict.

AI starts writing the code HTML Scripts

Chat assistants. ChatGPT launched on 30 November 2022. Within months, people were asking chat assistants to write whole pages of HTML, CSS and JavaScript from a description.

Assistants in the editor. Code assistants now sit inside editors such as VS Code. They suggest the next lines, explain errors and can change many files at once.

A generated page can look right and still be wrong. Here is the kind of contact form an assistant might produce:

<form>
  <input type="text" placeholder="Name">
  <input type="email" placeholder="Email">
  <button>Send</button>
</form>

It has no <label> elements, and placeholder text disappears as soon as you type. It has no action or method, so it sends nothing anywhere, and nothing checks what arrives. Someone still has to read the code, run the validator and test it. The skills from earlier chapters matter more, not less, when a machine writes the first draft.

Search starts answering for you Server

In May 2024, Google began showing AI Overviews in the United States: a written answer above the links.

Since the late 1990s the deal was simple: a search engine sent visitors to your site, and your site got the readers. An answer at the top of the page changes that deal. The answer is built from other people's pages, and fewer searchers click through to read them. If nobody visits the site that wrote the answer, how does that site keep paying to exist?

Who is allowed to read your site? Server

A file called robots.txt, at the root of a site, asks robots to stay out of some or all of it. It is a request, not a lock. These two lines ask OpenAI's crawler to stay away from the whole site:

User-agent: GPTBot
Disallow: /
  • 1994. Martijn Koster proposes robots.txt for the first web crawlers. It becomes an internet standard, RFC 9309, only in 2022.
  • August 2023. OpenAI publishes the name of its crawler, GPTBot, so sites can block it.
  • September 2024. A proposal called llms.txt suggests the opposite: a plain summary of a site, written for AI tools to read. It is a proposal, not a standard.
  • July 2025. Cloudflare starts blocking AI crawlers by default on new sites it protects. Well-behaved crawlers follow robots.txt, and badly behaved ones ignore it, which is why Cloudflare blocks at the server instead.

Some visitors are not people HTML

AI agents can now open a page, read it, click buttons and fill in forms for a person. They read the HTML much as a screen reader does. Two buttons that look the same on screen can read very differently to a machine:

<button>Send</button>              → button "Send"
<div class="btn">Send</div>      → text "Send" (not a button)

A real button, a labelled input and proper headings help a blind visitor, a search engine and an agent at the same time. A div pretending to be a button helps none of them. Semantic HTML was always about accessibility, and it now also decides how well machines understand a site.

Discuss
  1. Should a site be able to say no to AI crawlers? Who decides?
  2. If an AI answer uses your page, what do you think you are owed?
  3. Would you publish a site an AI wrote without reading the code?

These questions are being argued in courts and parliaments now, and reasonable people disagree on each one.

Chapter 7 · Today: Putting it together

This chapter in the other formats: the slides · the era page

Which jobs moved from scripts to HTML and CSS, how the four parts fit, and how to keep a site safe. Everything in this chapter applies to any site you build.

A rollover, then and now Scripts CSS

Both versions below change a box's colour when the pointer moves over it. The first uses a script written into the tag, as pages did around 1999. The second uses one CSS rule.

1999: a script in the tag

<div
  onmouseover="this.style.background='orange'"
  onmouseout="this.style.background='navy'">
  Point at me
</div>

Today: one CSS rule

<div class="box">Point at me</div>

.box:hover {
  background: orange;
}

The CSS version is shorter, keeps the look in one place, and still works if scripts are switched off. It is also far easier to change across a whole site. The job moved from scripts to CSS.

The years are when the feature worked in every major browser, not when it was first proposed. Scripts still do what HTML and CSS cannot: add up an order, remember a visitor, and fetch data without reloading the page.

Three tiers, three jobs HTML CSS Scripts Server

A dynamic site splits its work into three tiers. The application tier is sometimes called middleware. Follow a search through it: the visitor types in the browser, the application tier checks the request and asks the database, the database returns rows, and the application sends them back, often as JSON. Keeping the tiers apart means each one can be changed, secured or made bigger without rebuilding the others. A desktop database, by contrast, serves one person on one machine.

The browser helps. The server protects. Server Scripts

AttackWhat happensThe defence
SQL injection ServerAn attacker types SQL into a form to change the query the server runs.A parameterised query, which keeps what they typed apart from the SQL.
Cross-site scripting ScriptsAn attacker gets a script into a page that other visitors see.Escape all output, so text never runs as code.
Stolen passwords ServerA database leaks, and every password in it is readable.Store a hash, never the password. A hash cannot be turned back into the password.
-- unsafe: the input is glued into the SQL
"SELECT * FROM users WHERE name = '" + name + "'"

-- safe: the input travels separately, as a parameter
SELECT * FROM users WHERE name = ?

A form that checks itself with required and pattern helps the visitor. Anyone can bypass it, so the server must check every request again. Browser checks are a convenience for the visitor, never a defence.

What came next, and what it raises

There is no single agreed name for the period after Web 2.0. Some people call it Web 3.0, and they mean different things by it. Each change below raises a question worth talking over.

Questions to talk over

Each question has more than one good answer. Pick one, and back it up with an example from these notes.

  1. Pick a site you use every day. Which parts feel like Web 1.0, and which like Web 2.0?
  2. Why might a job move from a script into HTML?
  3. For a small site, would you choose plain HTML and CSS, WordPress, or a framework? Why?
  4. What can a server do that a browser never should?
  5. Open a site on your phone and on a laptop. Is it responsive? How can you tell?
