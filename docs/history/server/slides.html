Chapter 1 · 1966 to 1986

Data learns to sit in tables

Before the web, banks and airlines already needed computers that remembered things. The answer they settled on was the table.

Database

This chapter is older than the web by twenty years, and it explains the ideas that almost every web database still uses: tables, rows, keys and SQL.

1966 to 1970

Database

First, data lived in trees

A tree of records

IBM’s IMS, built for the Apollo programme in the late 1960s, stored data as a tree. A customer record held its orders, and each order held its items.

Follow the path

To find something, a program walked down the tree one level at a time. A new kind of question often meant writing a new program.

Customer → Order 17 → Item 3

The data was fast to read along the paths the designers planned, and slow or impossible to read along any other path.

IMS is still in use in some banks. The point for students: the shape of the storage decided which questions you could ask. The next slide shows the idea that broke that link.

1970

Database

Codd: put everything in tables

In 1970 Edgar F. Codd, a mathematician at IBM, published “A Relational Model of Data for Large Shared Data Banks”.

Every fact goes in a table of rows and columns. A key links one table to another. You say what you want, and the database works out how to find it.

products and sales

products
id  name    price
1   Crisps  1.20
2   Water   0.90

sales
id  product_id  sold_at
1   2           09:14

The number 2 in sales points at Water in products. That pointer is a foreign key.

Codd’s paper appeared in Communications of the ACM in June 1970. IBM was slow to build it because IMS made money, so other companies got there first. The two small tables on the slide are the pattern for a shop: one table of things for sale and one of sales.

1974 to 1986

Database

SQL: one language for asking

Researchers at IBM wrote a language for Codd’s tables, first called SEQUEL and later SQL. A question in SQL reads almost like English.

SELECT name, price FROM products WHERE price < 1;

1974

SEQUEL is described at IBM, as part of a research system called System R.

1979

The company that became Oracle sells the first commercial SQL database.

1986

SQL becomes an official standard, so the same language works across products.

SQL is now over fifty years old, and anyone who builds a site with a database will write it. The standard is why SQL learned in SQLite mostly works in MySQL and PostgreSQL too, with small differences.

Chapter 2 · 1990 to 1995

The first servers hand out files

A web server begins as a simple program: it waits for a request, finds a file and sends it back.

Server

HTML

The browser asks for a page, and a program on another computer answers. This chapter is about that program.

1990

Server

A server is a program that listens

Tim Berners-Lee wrote the first web server at CERN in 1990. It listened on a network port, read each request, found the matching file on its disk and sent it back.

If the file was missing, it answered with a status code. 404 still means “not found”.

a request and its answer

GET /hypertext/WWW/TheProject.html HTTP/1.0

HTTP/1.0 200 OK
Content-Type: text/html

<h1>World Wide Web</h1>…

Every request since works this way: a method, a path, then a status and a body.

The CERN server was called CERN httpd; the d stands for daemon, a program that runs in the background. The browser’s developer tools show these messages for any site: open the Network tab and reload.

1993

Server

HTML

CGI: the server runs a program

The idea

The Common Gateway Interface, from NCSA in 1993, let a server run a program and send back whatever that program printed, instead of a stored file.

What it made possible

A form could now send data to a script on the server, often written in Perl. The script could search, count or save, then print a fresh HTML page.

Example: the 1990s guestbook and hit counter

For the first time the page did not exist until somebody asked for it. That is a dynamic page.

CGI started a new program for every request, which was slow when many people visited. Later server languages kept one program running to avoid that cost. The folder name cgi-bin survives on old servers today.

1995

Server

Apache, and the server log

In 1995 a group of webmasters collected their fixes, or patches, to the NCSA server and released them as Apache. It became the most used web server for many years.

Like most servers, Apache writes one line to a log for every request. The log is how you find out who asked for what, and what went wrong.

A line of a log

203.0.113.7 - - [17/Nov/2026:09:14:02] "GET /index.html HTTP/1.1" 200 5120

Read it as

Who asked, when, which method and path, the status code, and the size of the answer in bytes.

The name is often explained as “a patchy server”, which the Apache project itself has said is a story added afterwards. Reading logs is a real job skill, and the first place to look when something breaks.

Chapter 3 · 1995 to 2004

Cheap hosting and free software put a database behind ordinary websites. The server now remembers.

Database

Many sites still follow the pattern in this chapter: a server language, a SQL database and HTML built on each request.

1995 to 1998

Server

Database

LAMP: a free stack for everyone

Linux

A free operating system for the server.

Apache

The web server that receives each request.

MySQL

A free SQL database, first released in 1995.

PHP

A language mixed into HTML, also from 1995.

A German magazine named the four together LAMP in 1998. Shared hosting with LAMP cost a few euro a month, so blogs, forums and shops could all keep their data in a database.

WordPress, which runs a large share of the web, is still a LAMP application. PostgreSQL, the other big free database, took its name in 1996. Perl and Python also filled the P in some versions.

1994 onwards

Server

Database

How the server remembers you

Cookies

From 1994, a server could hand the browser a small cookie, and the browser sent it back with every later request.

Set-Cookie: session=8f3a…

Sessions

The cookie holds only an id. The server keeps the real details, such as who you are and what is in your basket, in its own memory or database.

8f3a… → user 42, basket [2, 7]

HTTP forgets each request as soon as it ends. Cookies and sessions are how a login or a shopping basket survives from one page to the next.

This is the link to security later: if someone steals the session id, they become you. That is why session cookies should be marked HttpOnly and sent only over HTTPS.

1998

Server

Database

SQL injection: when input becomes code

In 1998 a security researcher called rain.forest.puppy described how text typed into a form could change the SQL a server ran. The attack is called SQL injection.

The cause is building a query by gluing strings together. The cure is a parameterised query: the SQL and the data travel separately.

the mistake, and the fix

# glued together: unsafe
sql = "SELECT * FROM users WHERE name = '" + name + "'"

# typed into the form:
' OR '1'='1

# parameterised: safe
db.execute("SELECT * FROM users WHERE name = ?", [name])

Over twenty-five years later, injection is still on OWASP’s list of the most common risks.

Walk through the example slowly. The typed text closes the quote early, then adds a condition that is always true, so the query returns every user. With a parameter, the same text is only a strange name that matches nobody.

2000 to 2002

Server

Scripts

Servers start answering with data

In 2000 Roy Fielding described REST in his PhD thesis: a way to design a server around resources, each with its own address, read and changed with the HTTP methods.

Soon after, JSON gave servers a light way to send data instead of whole pages. A script in the browser then decides how to show it.

GET /api/products/2

Read one product.

POST /api/sales

Record a new sale.

{ "id": 2, "name": "Water", "price": 0.9 }

The answer, as JSON.

Most web APIs today follow this design. On the browser side, a script sends the request and turns the JSON into part of the page.

Chapter 4 · 2003 to 2010

Frameworks, caches and NoSQL

Sites with millions of users push servers and databases to their limits, and new tools appear to cope.

Server

Database

Three ideas in this chapter: frameworks that write the repetitive code, caches that remember answers, and databases that give up some of SQL's rules to grow bigger.

2004 and 2005

Server

Database

Frameworks and the ORM

Ruby on Rails in 2004 and Django, in Python, in 2005 gave every new project the same folders, routes and database setup.

An ORM, an object-relational mapper, lets the program treat rows as objects. The framework writes the SQL.

the same question, twice

# with an ORM (Django)
Product.objects.filter(price__lt=1)

# the SQL it writes for you
SELECT * FROM products
WHERE price < 1;

An ORM saves typing and guards against injection. It also hides the SQL, so slow queries can go unnoticed.

Migrations also came with these frameworks: small files that change the database’s tables step by step, so every copy of the project has the same structure. Laravel later brought the same ideas to PHP.

2003

Server

Database

Caching: remember the answer

The problem

A popular page asked the database the same question thousands of times a minute.

The fix

memcached, written in 2003 for the LiveJournal blog site, kept recent answers in memory. The server checks the cache first and asks the database only when the cache has nothing.

cache hit: fast · cache miss: ask the database

A cache trades freshness for speed. The hard part is knowing when a remembered answer has gone out of date.

There is an old joke that the two hardest problems in computing are naming things and cache invalidation. Browsers cache too, which is why a hard refresh sometimes fixes a page.

2006 to 2009

Database

NoSQL: bigger, with fewer rules

Google and Amazon described databases that spread data over thousands of machines: Bigtable in 2006 and Dynamo in 2007. To grow that big, they gave up some of what SQL databases promise, such as joins between tables.

In 2009 a meetup in San Francisco gave the movement a name: NoSQL, later read as “not only SQL”.

MongoDB, 2009

Stores documents shaped like JSON, so one record can hold nested data.

Redis, 2009

Keeps keys and values in memory, very fast. Often used as a cache.

Still SQL, today

Most new projects still choose a SQL database, and many SQL databases now store JSON too.

Keep this balanced. NoSQL suits some jobs, such as huge volumes of simple records, and suits others badly, such as money, where every sale must add up. Ask which kind a small shop needs, and why.

2009

Server

Scripts

JavaScript on the server

One thread, many visitors

Node.js, from 2009, handles thousands of open connections in one program, by never waiting idle for the disk or the database.

One language at both ends

The same JavaScript, or TypeScript, can now run in the browser and on the server.

Example: a TypeScript server and TypeScript in the page

The point here is the server: Node changed how one program can wait for many things at once.

Python, PHP and Ruby servers can do the same with the right tools. Node made this way of waiting the default.

Chapter 5 · 2006 to 2019

Someone else’s computer

Servers move out of the back room and into rented data centres. You pay for what you use.

Server

Database

The phrase “the cloud is just someone else’s computer” is a joke, and it is also accurate. This chapter explains what is rented and why.

2006

Server

Database

Renting servers by the hour

Before 2006 a company that wanted a server bought one, installed it and kept it running. A busy day meant buying more, and a quiet month left them idle.

Amazon began renting storage and computers over the internet. A new server took minutes instead of weeks.

March 2006

Amazon S3 stores files for anyone, priced per gigabyte.

August 2006

Amazon EC2 rents whole virtual servers, priced by the hour.

Later

Google, Microsoft and others offer the same. Managed databases arrive, where the provider runs the database for you.

This is when the server stopped being a box that a business owned. A site on GitHub Pages or a free hosted database is a descendant.

2013 and 2014

Server

Containers: it works on my machine, and on yours

Docker, 2013

A container packs a program together with everything it needs to run. The same container runs the same way on a laptop and in a data centre.

FROM python:3.12 · COPY . /app · CMD python server.py

Kubernetes, 2014

Google released a system for running many containers across many machines, restarting any that fail and adding more when traffic grows.

Containers ended a long-running excuse: “it works on my machine”.

The three-line example is a simplified Dockerfile. Anyone who works with servers will meet Docker sooner or later.

2014 onwards

Server

Database

Serverless: just the function

Functions on demand

AWS Lambda, announced in November 2014, runs one function each time a request arrives. Nobody keeps a server running between requests.

Managed data

Hosted databases and services such as Firebase let a small team store data without running a database server themselves.

There are still servers, of course. “Serverless” means that somebody else looks after them.

Serverless is cheap for quiet sites and can be expensive for busy ones. It also brings back the CGI pattern from chapter 2 in a new form: start, answer one request, stop.

2017 and 2018

Database

Server

Data comes with rules

Breaches

In 2017 attackers took the personal data of about 147 million people from Equifax, through a server that had missed a security update.

GDPR, 2018

The EU’s data protection law began to apply on 25 May 2018. A site must collect only the data it needs, protect it and delete it on request.

A database is now a responsibility as well as a tool. Every column you add is data you must protect.

The Equifax breach exploited a flaw in Apache Struts, a Java framework, that had a fix available two months earlier. Updates matter. A question to ask: does a small online shop need each buyer’s date of birth?

Chapter 6 · 2020 to now

Data for AI

AI systems need data to learn from and data to look things up in. Databases learn to search by meaning.

Database

Server

This chapter has no settled ending. Present the ideas and dates, then let the class discuss.

2013 onwards

Database

Meaning as a list of numbers

An embedding turns a piece of text into a long list of numbers, called a vector. Texts with similar meanings get similar vectors.

A database can then find the rows closest in meaning to a question, even when they share no words with it.

a vector search, in SQL

-- pgvector, an add-on for PostgreSQL
SELECT title FROM notes
ORDER BY embedding <-> :question
LIMIT 3;

The <-> operator measures the distance between two vectors. Smaller means closer in meaning.

Real embeddings have hundreds or thousands of numbers. A version with only two numbers can be drawn on a flat map, which is a good way to explain the idea. pgvector first appeared in 2021, and SQLite and MySQL now have similar features.

2020 to 2023

Database

Server

Look it up, then answer

A language model only knows what was in its training data. To answer questions about your own documents, it needs to look them up first.

This pattern is called retrieval-augmented generation, or RAG: a server finds the closest rows in a vector database, then hands them to the model along with the question.

2020

Researchers at Facebook AI name and describe retrieval-augmented generation.

2021

pgvector adds vector search to PostgreSQL.

2023

Vector databases become a product category of their own, as chat assistants spread.

RAG is a three-tier application in disguise: a front end asks, a server program decides, a database remembers. Only the kind of search is new.

2023 onwards

Server

The servers’ new visitors

Crawlers

AI companies send crawlers to read the web for training data. Many sites saw their server logs fill with bots and their hosting bills rise.

User-agent: GPTBot

The defences

robots.txt asks crawlers to stay away. Rate limits slow down any visitor that asks too fast. Some hosts now block AI crawlers by default.

The log file from chapter 2 is where a site owner first notices this.

The angle here is cost: every request uses the server’s time and someone pays for it. A rate limit answers with status 429, Too Many Requests.

Discuss

Database

Questions without settled answers

Whose data?

If your writing helped train a model, should you have been asked? Should you be paid?

Forgetting

GDPR gives you a right to have your data deleted. How would anyone delete it from a trained model?

Trust

When an assistant answers from your own documents, how would you check that it read them correctly?

Reasonable people disagree on all three. Give each side a fair hearing.

These questions are being argued in courts and parliaments now. Keep the discussion open and make sure students hear the strongest case on each side.

The journey of one click

Browser

A click runs a script, which sends a request.

POST /api/buy {id: 2}

Then the same road in reverse: the row count comes back, the server answers with JSON and a status code, and the script updates the page. Every chapter of this history is one part of that road.

Today

Server

Database

Five habits that keep a server safe

Parameters

Never glue input into SQL. Send it as a parameter.

Hashes

Store a slow hash of each password, never the password.

Check again

Check every request on the server, even if the page checked it first.

HTTPS

Encrypt every request, so no one can read or change it on the way.

Updates

Install security updates promptly. Equifax waited two months.

None of these is new. Each one answers a mistake from earlier in this history.

Each habit maps to a chapter: parameters to 1998, hashes and breaches to 2017, checking on the server to the CGI forms of 1993, HTTPS to the free certificates of 2015, updates to Equifax. The OWASP Top 10 is the list to show next.

Today

Database

SQL is still here

SQLite

A whole SQL database in one file, first released in 2000. It is in every phone and every web browser, and probably the most used database in the world.

PostgreSQL and MySQL

The free databases of chapter 3 still run a large share of the web, now with JSON and vector features added.

Fifty years after Codd, the table and the SELECT statement are still the place to start.

SQLite needs no database server at all, which makes it a good first database. It can even run inside a web page, compiled to WebAssembly.
