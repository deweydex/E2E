Introduction

Behind the Page

Most histories of the web watch from the browser. This one walks round to the back of the page and watches the computers that answer. Every chapter adds one stop on the road a click travels: the request, the route that handles it, the SQL that asks the database, and the rows that come back.

One green box, opened up

Every website is built from a few parts, and each part has a colour. Each section of these notes carries a tag in that colour for every part it is about, with the name written on it, so nobody has to rely on colour alone.

HTML is the structure of the page the server sends back.
CSS is the look of that page. The server only delivers it.
Scripts are code in the browser that sends requests and shows replies.
Server is a program that listens for requests and decides what to send.
Database is the place that remembers data after every request has ended.

Seen from the browser, everything behind the page looks like one green box called the server. These notes open the box: the program that answers stays green, and the database that remembers is purple. Most of this history lives in green and purple, and the front-end colours appear only where the browser meets the server.

Before we start: history is messy

The dates in these notes mark when something appeared or became a standard. They do not mark when everyone used it. Every technology here spread at its own speed, overlapped with older ones for years, and depended on others that came before it.

How a new technology spreads

In 1962 the sociologist Everett Rogers described how new ideas spread through a group of people in his book Diffusion of Innovations. He sorted people into five groups by when they take up something new.

GroupShareWho they are
Innovators2.5%Try something while it is still rough and risky
Early adopters13.5%Take it up once it shows promise, and others watch them
Early majority34%Wait until it works reliably
Late majority34%Join once most people already use it
Laggards16%Switch last, often only when the old way stops working

The bell curve shows how many people adopt in each period. Add them up, and the total so far follows an S-curve: slow at first, then steep, then flat. The percentages are idealised, and real technologies rarely follow the shape exactly.

Chapter 1 · 1966 to 1986: Data learns to sit in tables

Before the web, banks and airlines already needed computers that remembered things. The answer they settled on was the table, and almost every web database still uses the ideas in this chapter: tables, rows, keys and SQL.

First, data lived in trees Database

IBM's IMS, built for the Apollo space programme in the late 1960s, stored data as a tree. A customer record held its orders, and each order held its items.

CUSTOMER  Aoife
  ORDER 17
    ITEM  Crisps  1.20
    ITEM  Water   0.90
  ORDER 18
    ITEM  Apple   0.50

To find something, a program walked down the tree one level at a time: Customer, then Order 17, then Item 3. The data was fast to read along the paths the designers planned, and slow or impossible to read along any other path. A new kind of question often meant writing a new program, so the shape of the storage decided which questions you could ask. IMS is still in use in some banks.

Codd: put everything in tables Database

In June 1970 Edgar F. Codd, a mathematician at IBM, published "A Relational Model of Data for Large Shared Data Banks". Every fact goes in a table of rows and columns. A key links one table to another. You say what you want, and the database works out how to find it.

products

id  name    price
1   Crisps  1.20
2   Water   0.90

sales

id  product_id  sold_at
1   2           09:14

The number 2 in sales points at Water in products. That pointer is a foreign key. The two tables are the pattern for a shop: one table of things for sale and one of sales. IBM was slow to build Codd's idea because IMS made money, so other companies got there first.

SQL: one language for asking Database

Researchers at IBM wrote a language for Codd's tables, first called SEQUEL and later SQL. A question in SQL reads almost like English:

SELECT name, price FROM products WHERE price < 1;
  • 1974. SEQUEL is described at IBM, as part of a research system called System R.
  • 1979. The company that became Oracle sells the first commercial SQL database.
  • 1986. SQL becomes an official standard, so the same language works across products.

SQL is now over fifty years old, and anyone who builds a site with a database will write it. The standard is why SQL learned in SQLite mostly works in MySQL and PostgreSQL too, with small differences.

Chapter 2 · 1990 to 1995: The first servers hand out files

A web server begins as a simple program: it waits for a request, finds a file and sends it back. The browser asks for a page, and a program on another computer answers.

A server is a program that listens Server

Tim Berners-Lee wrote the first web server at CERN in 1990. It listened on a network port, read each request, found the matching file on its disk and sent it back. If the file was missing, it answered with a status code instead. 404 still means "Not Found".

GET /hypertext/WWW/TheProject.html HTTP/1.0

HTTP/1.0 200 OK
Content-Type: text/html

<h1>World Wide Web</h1>…

Every request since works this way: a method and a path go in, and a status and a body come back. The first server was called CERN httpd; the d stands for daemon, a program that runs in the background. Your browser's developer tools show these messages for any site: open the Network tab and reload the page.

CGI: the server runs a program Server HTML

The Common Gateway Interface, from NCSA in 1993, let a server run a program and send back whatever that program printed, instead of a stored file. A form could now send data to a script on the server, often written in Perl. The script could search, count or save, then print a fresh HTML page.

#!/usr/bin/perl
print "Content-Type: text/html\n\n";
print "<h1>Hello, $name</h1>";

For the first time the page did not exist until somebody asked for it. That is a dynamic page. The 1990s guestbook and hit counter worked this way. CGI started a new program for every request, which was slow when many people visited, and later server languages kept one program running to avoid that cost.

Apache, and the server log Server

In 1995 a group of webmasters collected their fixes, or patches, to the NCSA server and released them as Apache. It became the most used web server for many years. Like most servers, Apache writes one line to a log for every request:

203.0.113.7 - - [17/Nov/2026:09:14:02] "GET /index.html HTTP/1.1" 200 5120

Read it as: who asked, when, which method and path, the status code, and the size of the answer in bytes. The log is how you find out who asked for what and what went wrong, and it is the first place to look when something breaks. The name Apache is often explained as "a patchy server", which the Apache project itself has said is a story added afterwards.

Chapter 3 · 1995 to 2004: Pages built from a database

Cheap hosting and free software put a database behind ordinary websites, and the server now remembers. Many sites still follow this pattern: a server language, a SQL database and HTML built on each request.

LAMP: a free stack for everyone Server Database

LetterSoftwareIts job
LLinuxA free operating system for the server
AApacheThe web server that receives each request
MMySQLA free SQL database, first released in 1995
PPHPA language mixed into HTML, also from 1995

A German magazine named the four together LAMP in 1998. Shared hosting with LAMP cost a few euro a month, so blogs, forums and shops could all keep their data in a database. WordPress, which runs a large share of the web, is still a LAMP application. PostgreSQL, the other big free database, took its name in 1996, and Perl and Python also filled the P in some versions.

How the server remembers you Server Database

HTTP forgets each request as soon as it ends. Cookies and sessions are how a login or a shopping basket survives from one page to the next.

  • Cookies. From 1994, a server could hand the browser a small cookie, and the browser sent it back with every later request.
  • Sessions. The cookie holds only an id. The server keeps the real details, such as who you are and what is in your basket, in its own memory or database.
Set-Cookie: session=8f3a91c2; HttpOnly; Secure
sessions:   8f3a91c2 → user 42, basket [2, 7]

If someone steals the session id, they become you. That is why session cookies should be marked HttpOnly, so scripts cannot read them, and sent only over HTTPS.

SQL injection: when input becomes code Server Database

In 1998 a security researcher called rain.forest.puppy described how text typed into a form could change the SQL a server ran. The attack is called SQL injection. The cause is building a query by gluing strings together:

# glued together: unsafe
sql = "SELECT * FROM users WHERE name = '" + name + "'"

# typed into the form:
' OR '1'='1

# the query the database receives:
SELECT * FROM users WHERE name = '' OR '1'='1'

The typed text closes the quote early, then adds a condition that is always true, so the query returns every user. The cure is a parameterised query, where the SQL and the data travel separately:

db.execute("SELECT * FROM users WHERE name = ?", [name])

With a parameter, the same text is only a strange name that matches nobody. Over twenty-five years later, injection is still on OWASP's list of the most common risks.

Servers start answering with data Server Scripts

In 2000 Roy Fielding described REST in his PhD thesis: a way to design a server around resources, each with its own address, read and changed with the HTTP methods. Soon after, JSON gave servers a light way to send data instead of whole pages. A script in the browser then decides how to show it.

RequestMeaning
GET /api/products/2Read one product.
POST /api/salesRecord a new sale.
{ "id": 2, "name": "Water", "price": 0.9 }

Most web APIs today follow this design. On the browser side, a script sends the request and turns the JSON into part of the page.

Chapter 4 · 2003 to 2010: Frameworks, caches and NoSQL

Sites with millions of users push servers and databases to their limits, and new tools appear to cope. Three ideas mark this chapter: frameworks that write the repetitive code, caches that remember answers, and databases that give up some of SQL's rules to grow bigger.

Frameworks and the ORM Server Database

Ruby on Rails in 2004 and Django, in Python, in 2005 gave every new project the same folders, routes and database setup. An ORM, an object-relational mapper, lets the program treat rows as objects, and the framework writes the SQL.

With an ORM (Django)

Product.objects.filter(price__lt=1)

The SQL it writes for you

SELECT * FROM products
WHERE price < 1;

An ORM saves typing and guards against injection. It also hides the SQL, so slow queries can go unnoticed. Migrations also came with these frameworks: small files that change the database's tables step by step, so every copy of the project has the same structure. Laravel later brought the same ideas to PHP.

Caching: remember the answer Server Database

A popular page asked the database the same question thousands of times a minute. memcached, written in 2003 for the LiveJournal blog site, kept recent answers in memory. The server checks the cache first and asks the database only when the cache has nothing.

A cache trades freshness for speed. The hard part is knowing when a remembered answer has gone out of date: if a price changes in the database, the cache may keep serving the old one until it is cleared. Browsers cache too, which is why a hard refresh sometimes fixes a page.

NoSQL: bigger, with fewer rules Database

Google and Amazon described databases that spread data over thousands of machines: Bigtable in 2006 and Dynamo in 2007. To grow that big, they gave up some of what SQL databases promise, such as joins between tables. In 2009 a meetup in San Francisco gave the movement a name: NoSQL, later read as "not only SQL".

The same order as tables

orders
id  customer
17  aoife

order_items
order_id  item    price
17        crisps  1.20
17        water   0.90

The same order as a document

{
  "_id": 17,
  "customer": "aoife",
  "items": [
    { "item": "crisps", "price": 1.20 },
    { "item": "water",  "price": 0.90 }
  ]
}
  • MongoDB, 2009, stores documents shaped like JSON, so one record can hold nested data.
  • Redis, 2009, keeps keys and values in memory and is very fast. It is often used as a cache.
  • Still SQL, today. Most new projects still choose a SQL database, and many SQL databases now store JSON too.

NoSQL suits some jobs, such as huge volumes of simple records, and suits others badly, such as money, where every sale must add up. A document keeps the whole order in one place, which is quick to read. Tables keep each fact once, which is safer when the numbers must agree.

JavaScript on the server Server Scripts

Node.js, from 2009, handles thousands of open connections in one program, because it never waits idle for the disk or the database. While one request waits for the database, Node works on another. The same JavaScript, or TypeScript, can now run in the browser and on the server. Python, PHP and Ruby servers can do the same with the right tools, but Node made this way of waiting the default.

Chapter 5 · 2006 to 2019: Someone else’s computer

Servers move out of the back room and into rented data centres, and you pay for what you use. The phrase "the cloud is just someone else's computer" is a joke, and it is also accurate.

Renting servers by the hour Server Database

Before 2006, a company that wanted a server bought one, installed it and kept it running. A busy day meant buying more, and a quiet month left them idle. Then Amazon began renting storage and computers over the internet, and a new server took minutes instead of weeks.

  • March 2006. Amazon S3 stores files for anyone, priced per gigabyte.
  • August 2006. Amazon EC2 rents whole virtual servers, priced by the hour.
  • Later. Google, Microsoft and others offer the same. Managed databases arrive, where the provider runs the database for you.

This is when the server stopped being a box that a business owned. A site on GitHub Pages or a free hosted database is a descendant.

Containers: it works on my machine, and on yours Server

A container packs a program together with everything it needs to run, so the same container runs the same way on a laptop and in a data centre. Docker made containers easy in 2013. In 2014 Google released Kubernetes, a system for running many containers across many machines, restarting any that fail and adding more when traffic grows.

# Dockerfile
FROM python:3.12
COPY . /app
CMD python /app/server.py

Containers ended a long-running excuse: "it works on my machine". Anyone who works with servers will meet Docker sooner or later.

Serverless: just the function Server Database

  • Functions on demand. AWS Lambda, announced in November 2014, runs one function each time a request arrives. Nobody keeps a server running between requests.
  • Managed data. Hosted databases and services such as Firebase let a small team store data without running a database server themselves.
Way to run a siteWhat runsWhat you pay for
Own one serverOne machine, all the timeEvery hour, busy or not
Rent and scaleMore rented servers as traffic growsThe servers running each hour
ServerlessA function per request, nothing in betweenEach request

There are still servers, of course. "Serverless" means that somebody else looks after them. Serverless is cheap for quiet sites and can be expensive for busy ones. It also brings back the CGI pattern from chapter 2 in a new form: start, answer one request, stop.

Data comes with rules Database Server

Breaches. In 2017 attackers took the personal data of about 147 million people from Equifax, through a server that had missed a security update. The flaw was in Apache Struts, a Java web framework, and a fix had been available for about two months.

GDPR, 2018. The EU's data protection law began to apply on 25 May 2018. A site must collect only the data it needs, protect it and delete it on request.

A database is now a responsibility as well as a tool. Every column you add is data you must protect. A question worth asking about any form: does a small online shop need each buyer's date of birth?

Chapter 6 · 2020 to now: Data for AI

AI systems need data to learn from and data to look things up in, and databases learn to search by meaning. This chapter has no settled ending, so it closes with questions.

Meaning as a list of numbers Database

An embedding turns a piece of text into a long list of numbers, called a vector. Texts with similar meanings get similar vectors. A database can then find the rows closest in meaning to a question, even when they share no words with it.

Real embeddings have hundreds or thousands of numbers. With only two numbers, each note can sit at a point on a flat map, and a question lands near the notes that mean something similar:

-- pgvector, an add-on for PostgreSQL
SELECT title FROM notes
ORDER BY embedding <-> :question
LIMIT 3;

The <-> operator measures the distance between two vectors, and a smaller distance means closer in meaning. pgvector first appeared in 2021, and SQLite and MySQL now have similar features.

Look it up, then answer Database Server

A language model only knows what was in its training data. To answer questions about your own documents, it needs to look them up first. This pattern is called retrieval-augmented generation, or RAG: a server finds the closest rows in a vector database, then hands them to the model along with the question.

  • 2020. Researchers at Facebook AI name and describe retrieval-augmented generation.
  • 2021. pgvector adds vector search to PostgreSQL.
  • 2023. Vector databases become a product category of their own, as chat assistants spread.

RAG is a three-tier application in disguise: a front end asks, a server program decides, a database remembers. Only the kind of search is new.

The servers’ new visitors Server

AI companies send crawlers to read the web for training data. Many sites saw their server logs fill with bots and their hosting bills rise.

66.249.66.1  "GET /notes/12"  200  Googlebot
20.15.240.9  "GET /notes/13"  200  GPTBot
20.15.240.9  "GET /notes/14"  200  GPTBot
20.15.240.9  "GET /notes/15"  429  GPTBot
81.17.4.22   "GET /notes/12"  200  Firefox

A site has three defences. robots.txt asks crawlers to stay away. A rate limit slows down any visitor that asks too fast, answering with status 429, Too Many Requests, as in the fourth line above. Some hosts now block AI crawlers by default. The angle here is cost: every request uses the server's time, and someone pays for it. The log file from chapter 2 is where a site owner first notices.

Questions without settled answers Database Server

  1. Whose data? If your writing helped train a model, should you have been asked? Should you be paid?
  2. Forgetting. GDPR gives you a right to have your data deleted. How would anyone delete it from a trained model?
  3. Trust. When an assistant answers from your own documents, how would you check that it read them correctly?

Reasonable people disagree on all three, and these questions are being argued in courts and parliaments now.

Chapter 7 · Today: Putting it together

One click, followed all the way to a database row and back, and the habits that keep it safe.

The journey of one click Scripts Server Database

UPDATE products SET stock = stock - 1
WHERE id = ? AND stock > 0;

Then the same road runs in reverse: the database reports how many rows changed, the server answers with JSON and a status code, and the script updates the page. Putting the stock check inside the UPDATE means two buyers at once cannot both take the last item. Every chapter of this history is one part of that road: the request from chapter 2, the SQL from chapter 1, the route and the JSON from chapter 3, and the framework habits from chapter 4.

Five habits that keep a server safe Server Database

HabitWhat it meansThe mistake it answers
ParametersNever glue input into SQL. Send it as a parameter.SQL injection, 1998
HashesStore a slow hash of each password, never the password.Leaked databases full of readable passwords
Check againCheck every request on the server, even if the page checked it first.Trusting the browser, since the CGI forms of 1993
HTTPSEncrypt every request, so no one can read or change it on the way.Plain HTTP, before free certificates in 2015
UpdatesInstall security updates promptly.Equifax, 2017

A slow hash, such as bcrypt or Argon2, turns a password into a fixed string that cannot be turned back:

id  name   password_hash
2   brian  $2b$12$Q9vWm0…   (60 characters, different for every user)

None of these habits is new. Each one answers a mistake from earlier in this history. The OWASP Top 10 is the list to read next.

SQL is still here Database

SQLite. A whole SQL database in one file, first released in 2000. It is in every phone and every web browser, and it is probably the most used database in the world. SQLite needs no database server at all, which makes it a good first database, and it can even run inside a web page, compiled to WebAssembly.

PostgreSQL and MySQL. The free databases of chapter 3 still run a large share of the web, now with JSON and vector features added.

Fifty years after Codd, the table and the SELECT statement are still the place to start.

Questions to talk over

Each question has more than one good answer. Pick one, and back it up with an example from these notes.

  1. Pick a site you use. What do you think lives on its server, and what in its database?
  2. What could happen if a visitor typed SQL into a site's search box?
  3. When would you choose a document database over SQL tables?
  4. What data does a site you use collect that it does not need?
  5. Find a status code in your browser's network tab. What does it mean? (Open the developer tools, choose the Network tab, reload a page and read the status column.)
