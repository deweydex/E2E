What happens when we save a file?

We’ll begin with a populated folder, select a file, and zoom into the structures and bytes behind it. We can follow its name to a file record, its stored content, and the bits that represent the text. Then we can explore how files are created, found and edited.

We begin with three things: a filename, a path telling us where to find it, and its contents. No knowledge of binary, hexadecimal or storage is assumed.

What we’re working towards

  • Distinguish a file’s contents, filename and path.
  • Explain why text in a running program is different from a saved file.
  • Follow what happens when a file is created, opened and edited.

Things we can explore

  • Zoom from a file browser to directory records, blocks, bytes and bits.
  • Open folders and find different files with the same name.
  • Connect file information (metadata) to the records that store it.
  • Follow a save, then explore why interrupted updates need recovery.

One idea, three common implementations
The operating system runs programs and manages resources. A filesystem organises named objects on a volume. Linux + ext4, macOS + APFS and Windows + NTFS are example pairings, not exclusive relationships.

What appears when?
Names, paths, contents and relevant Python examples are visible from the first step. File identifiers appear with directory entries. Size, permissions and locations appear when we introduce metadata and file records. Bits, decimal values and hex each receive their own interactive step before we decode text. Exact filesystem byte layouts and additional questions are optional extensions; they are not prerequisites for following the main explanation. Recovery and journalling appear during saving, where their purpose becomes concrete.
What we simplify
This page is a simulation; it cannot read or change your real files. Each chapter starts its own example. Editing an example field recalculates the current snapshot, rather than performing an operation on your device. Back and Next move between snapshots.
Directory entries, file records and contents all occupy storage; they can also be cached in RAM. Their boxes show relationships, not separate physical floors. The exact zoom example uses 4096-byte ext4 filesystem blocks. Simplified overview scenes in other chapters group bytes into four-byte teaching cells; those are not real allocation units. We omit detailed permissions, mounts, links, concurrent access, encryption, compression, sparse files and crash recovery. Background writes may happen between our snapshots.
Synchronisation requests are stronger than flushing a Python buffer. Exact crash-durability guarantees depend on the platform and device; file creation and atomic replacement may need additional directory or platform-specific synchronisation. NTFS resident data is explained as a detail: small contents can fit inside the file record rather than needing separate data blocks.
