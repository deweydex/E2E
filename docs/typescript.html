How a click reaches a database and comes back

Start hereFrom click to row and back again

Press Buy on a vending machine page and the number of snacks left changes a moment later. In this tutorial you build that whole machine, one piece at a time, and you watch a click travel from the page to a database and back.

You will build

  • A database that stores the machine's slots.
  • A server that answers requests about those slots.
  • A page with a Buy button.
  • A short script that connects the page to the server.

You will learn

  • What a database, a server and an API each do.
  • How a click becomes a request, a query and a changed screen.
  • How to watch that traffic in your browser.
Download the finished project (.zip)

You need

  • Node.js 22.18 or newer, which includes npm. From that version Node can run a TypeScript file directly.
  • A terminal and a code editor.
  • A browser with developer tools. Chrome, Edge and Firefox all have them.
  • Two packages, installed with npm: the TypeScript compiler and the type descriptions for Node. You use both only while you develop.

In this edition everything is TypeScript: the server, the setup script, the database code and the page's script. TypeScript is JavaScript with types added, which are labels that say what kind of value each variable holds, so that a tool can catch mistakes before the program runs. The page itself is plain HTML and CSS, and the script is about fifty lines.

A web page cannot open a network port, so no real server program is running. Five real things are running.

  • The data layer and the route table are copied out of the real server.ts when this page is built, with the types removed.
  • The real setup-db.ts creates the table.
  • sql.js supplies a real SQLite database in the page's memory.

The simulated part is the wire. No bytes travel between two programs, so Stations 3 and 9 are imitated. Two small files stand in for what a browser lacks: a wrapper that gives sql.js the interface of Node's SQLite module, and a replacement for the HTTP layer. The second is possible because the layers were kept apart.

Step 1Follow one click

In this step you will
  • Follow one click through twelve stations, from the button to the database and back to the screen.
  • See which program handles each station: the browser, the server or the database.
  • Meet the words that the later steps explain in detail. You do not need to remember them yet.

Press Buy on slot A1. The screen changes after a few milliseconds, and those milliseconds hold twelve stations. Use the buttons under the diagram to step through them.

Reference:The twelve stations as a list
  1. The browser notices the click. The page has a script that listens for clicks. It wakes up when you press Buy. A click is one kind of event, a message the browser creates whenever something happens on the page.
  2. The script builds a request. The script sends a message to the server, called a request. Here it says please buy one item from slot A1. It does this with fetch, a function that the browser provides.
  3. The request travels. The message goes to an address with two parts: the host, which is the computer, and the port, which is the program on that computer. Here both are on your own machine.
  4. The server chooses a handler. The server is a program that waits for requests. It reads the method and the path of the request, and picks the function that deals with it. That function is called the handler.
  5. The handler checks the input. The handler checks that the slot id looks right, such as A1. Anything else is turned away with a message. Checking input like this is called validation.
  6. The handler sends SQL to the database. SQL is the language for asking a database to find or change rows. The handler sends one SQL statement through a connection, which is an open line between the program and the database.
  7. The database changes the row. The database takes one away from the stock and says how many rows it changed. It does this as a transaction, which means the change either happens completely or not at all.
  8. The handler packages the result. The result becomes JSON, a text format that other programs can read. Only bytes can cross a network, so structured data has to become text first. This step is called serialising.
  9. The server sends a response. The response holds a status code that says how it went (200 means it worked), some headers that describe the message, and a body that carries the JSON.
  10. The reply reaches the script. The script receives the JSON and turns it back into an object. Waiting for a reply takes time, so fetch gives the script a promise, which stands for a value that has not arrived yet.
  11. The script changes the DOM. The DOM is the browser's live tree of the elements on the page. The script edits that tree: new text, or a button that becomes disabled.
  12. The browser repaints the screen. The browser notices that the tree has changed and redraws. You write no code for this step, and it is why the screen updates.
Keep these three ideas
  • The browser and the server are two separate programs. They work together by sending messages.
  • The database sits behind the server and never in front of it.
  • Each of the next steps builds one part of this picture.

Step 2Build the database

In this step you will
  • Create the vending machine's database as a file.
  • Run a script that fills it with four slots.
  • See the stored rows printed back.

Two ideas about TypeScript

  • A type says what kind of value a variable holds, such as a number or a text. A tool called the type checker reads these labels and reports mistakes before the program runs.
  • The labels exist only for the checker. Before the program runs they are erased, and ordinary JavaScript remains.
  • Node 22.18 and newer can run a TypeScript file directly by erasing the labels as it loads the file. That is type stripping, and it is why node src/server.ts needs no build step.
  • A browser cannot do this, so the page script goes through the compiler tsc, which writes a JavaScript file. The server uses stripping, and the page script uses the compiler.

Why a database?

A page forgets everything when it reloads, and a server forgets everything when it stops. The stock count has to live somewhere that outlasts both, and every visitor has to see the same count. A text file could hold the numbers, but then you would solve several hard problems yourself. A database has already solved them. A relational database keeps its data in tables of rows and columns.

A database gives you five things:

  • Persistence. The data survives when the programs stop.
  • Structure. A schema declares the tables, the columns and the type of each column.
  • Queries. SQL asks for exactly the rows you want, and the database finds them quickly.
  • Safe changes. A transaction makes a group of changes all-or-nothing, and it keeps simultaneous users from spoiling each other's work.
  • Rules. A constraint such as CHECK (stock >= 0) makes the database refuse bad data, even when a bug in your code tries to write it.

The machine needs one table. Its primary key, slot_id, is a column whose value differs in every row, so it identifies exactly one row.

slot_iditem_nameprice_centsstock
A1Sparkling Water1758
A2Salted Peanuts1255
B1Chocolate Bar2003
B2Oat Biscuits1500
Optional:Why the price is a whole number of cents

Computers store fractions in binary, and many decimal fractions cannot be written exactly in binary. In most languages 0.1 + 0.2 gives 0.30000000000000004. A shop that adds up prices like that will be wrong by a cent sooner or later. Whole numbers are exact, so the table stores 175 cents and the page converts to euros only when it shows the price.

Optional:Where SQLite fits

SQLite is a database that lives inside a library that your program loads. It keeps everything in one ordinary file, and it needs no installation and no separate server. Larger systems such as PostgreSQL and MySQL run as their own server programs. All of them speak SQL, so what you learn here carries over. SQLite is a quiet car park for a first driving lesson: it removes everything that is not the lesson.

Step 3Build the server and its API

In this step you will
  • Write the server in one file, in three layers.
  • Offer an API with three routes: list the slots, show one slot, buy from a slot.
  • Open the API in a browser and see JSON, with no page involved.

Two programs, one conversation

  • A client starts a conversation. Your browser is the client.
  • A server waits for conversations to start. Your TypeScript program is the server.
  • The client needs an address. The host says which computer, and the port says which program on that computer. We use host 127.0.0.1, which always means this computer, and port 8000.
  • Host, port and path together make a URL, such as http://127.0.0.1:8000/api/slots/A1/buy. The server reads the path to decide what to do.

Why the page never talks to the database

The visitor owns the browser. They can read every line of the page, change it, run any script in the console, or skip the page and send requests by hand. A check that exists only in the browser can always be skipped. So the rules of the machine live on the server, and the server is the only program with a route to the database.

Look at how Buy is designed. The browser names a slot and nothing else. It does not say what the price is or which SQL to run. Those decisions belong to the server.

A prediction to make first

Suppose the page sent { "slot": "A1", "price_cents": 0 } with every purchase and the server trusted it. What could a curious visitor do with the developer console? Which other parts of the design would still protect us, and which would not?

Design the API before you write it

An API (Application Programming Interface) is the part of a program that other programs may use. A web API offers it over HTTP, and usually replies in JSON. Designing one means four decisions:

  • Which things does it offer? Each thing gets a URL, called an endpoint. Ours are all the slots and each single slot.
  • Which actions are allowed? The method names the action. GET reads, and POST changes something.
  • What shape does the data have? The contract lists the fields and their types.
  • How are outcomes reported? A status code gives the category, and a JSON message gives the detail. 200 means success, 400 means the client asked badly, 404 means nothing is there, and 409 means the request clashes with the current state.
MethodURLWhat it doesOn successOn failure
GET/api/slotsLists every slot200 and a list of slotsNone expected
GET/api/slots/A1Shows one slot200 and one slot400 for a malformed id, 404 for a missing slot
POST/api/slots/A1/buyBuys one item200 and the updated slot400, 404, or 409 when sold out

Two shapes of JSON cross the network, a slot and an error:

A slot, followed by an error

{
  "slot_id": "A1",
  "item_name": "Sparkling Water",
  "price_cents": 175,
  "stock": 7
}

{ "error": "Oat Biscuits is sold out." }

The page and the server are written at different times. If the server renames stock to quantity, the page breaks without any warning. In this edition the contract appears twice in code, as a Slot type in the server and another in the page script. Each copy is checked only against its own program, so if they drift apart nothing warns you. A table like the one above gives both a single reference.

Build it in three layers

  • The data layer talks to the database and knows nothing about HTTP.
  • The route layer connects URLs to data functions and checks input.
  • The HTTP layer reads requests and writes responses, and the last lines start the server.
  • Each layer uses only the one beneath it, so you can change one without disturbing the others. The file lists the layers in this order.

Step 5Build the script

In this step you will
  • Write the script that asks the server for the slots.
  • Compile it to JavaScript for the browser.
  • Make the Buy button work, so the whole journey from Step 1 happens.

The script has one job: ask the server for data and change the page to match the reply. Everything with rules in it, such as the stock count and the validation, lives in the server. The script is TypeScript too, so the compiler checks it against the browser's own descriptions of the page.

The same fact in five shapes

The fact that slot A1 has seven items left takes five shapes on its way from the disk to the screen. The script you are about to write handles the last three.

1. A row in the database

slot_id | item_name       | price_cents | stock
A1      | Sparkling Water | 175         | 7
↓ selectOneSlot.get(slotId) returns the row as an object

2. A JavaScript object in the server

{ slot_id: 'A1', item_name: 'Sparkling Water', price_cents: 175, stock: 7 }
↓ JSON.stringify(...) serialises the object into text

3. Text on the network (JSON)

{"slot_id":"A1","item_name":"Sparkling Water","price_cents":175,"stock":7}
↓ response.json() parses the text into an object

4. An object in the browser's script

{ slot_id: "A1", item_name: "Sparkling Water", price_cents: 175, stock: 7 }
↓ createSlotCard copies the values into elements with textContent

5. Elements in the DOM

<p class="stock">7 left</p>
  • Only the third shape can cross the network, because a network carries text and bytes.
  • Serialising turns a structure into text. Parsing turns text back into a structure.
  • Every arrow is a place where something can go wrong: a key can be missing, a number can arrive as text, or a value can be empty.

Going deeperHTTP messages and status codes

You can build the whole project without reading this section. It is here for when you want to know exactly what the browser and the server say to each other.

  • A protocol is an agreement about the order and shape of messages.
  • HTTP (HyperText Transfer Protocol) is the agreement that browsers and web servers use.
  • Every exchange is two plain-text messages, a request and a response. Below is a real pair from the running project.

Status codes

The status code is a three digit number that tells the client how things went before it reads the body. The first digit gives the family: 2 means success, 4 means the client made a mistake, and 5 means the server did.

CodeNameWhen we send it
200OKThe request worked and the body holds the result.
400Bad RequestThe client sent something the server cannot make sense of, such as the slot id hello.
404Not FoundThe request was well formed, but nothing exists at that address, such as slot Z9.
409ConflictThe request was fine but clashes with the current state. Buying from a sold-out slot is a conflict.
500Internal Server ErrorSomething broke inside the server. The fault is ours, not the client's.

Methods

  • GET reads something and promises to change nothing. A method like that is safe.
  • POST asks the server to do something, and it may change data.
  • Browsers, link previews in chat apps and search engine crawlers send GET requests freely and may repeat them. If buying were a GET, a chat app that previews a link could buy a snack.
  • Buying is also not idempotent, because doing it twice does not leave the same result as doing it once. Reading is idempotent, so you can refresh a page as often as you like.

A server with no memory

HTTP is stateless: the server treats every request as new and remembers nothing between them. So the stock count lives in the database and never in a variable inside the server.

REST in one paragraph

Many web APIs follow a style called REST (Representational State Transfer). URLs name things with nouns, the method chooses the action, and each request is complete in itself. Our API borrows that style without following every rule of it.

Experiment 1: three kinds of sold out

  1. In the page, press Buy on the Chocolate Bar until it is sold out. The button greys out after the third press.
  2. Send the same purchase from a terminal, where no disabled button can stop you: curl -i -X POST http://127.0.0.1:8000/api/slots/B1/buy
  3. Try to break the rule inside the database: UPDATE inventory SET stock = -1 WHERE slot_id = 'A1';
What happened, and why
  • The terminal request returns 409 Conflict. The server refused, even though the page was bypassed.
  • The SQL fails with CHECK constraint failed: stock >= 0. The database refused, even though the server was bypassed.
  • Three layers, three jobs: the button is a courtesy, the server holds the rule and explains it, and the database is the last line of defence.

Experiment 2: two kinds of wrong address

Visit http://127.0.0.1:8000/api/slots/hello and then http://127.0.0.1:8000/api/slots/Z9. Guess each status code first.

What happened, and why
  • The first returns 400. hello is not shaped like a slot id, so the client asked badly.
  • The second returns 404. Z9 has the right shape but no such slot exists.
  • Two codes let a client tell a typing mistake from a missing item.

Experiment 3: joining strings versus passing parameters

Run node src/injection-demo.ts. It looks up a slot twice, once with a normal id and once with the text x' OR '1'='1, using two ways of building the query.

Output

The user typed: A1
Joined into the string:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = 'A1'
  rows returned: 1
Passed as a parameter:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = ? with value "A1"
  rows returned: 1

The user typed: x' OR '1'='1
Joined into the string:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = 'x' OR '1'='1'
  rows returned: 4
Passed as a parameter:
  SQL sent to the database: SELECT item_name, stock FROM inventory WHERE slot_id = ? with value "x' OR '1'='1"
  rows returned: 0
What happened, and why
  • With joined strings, the typed text becomes part of the SQL. The condition OR '1'='1' is true for every row, so all four rows come back. This attack is SQL injection.
  • With a parameter, the database receives the SQL and the value separately. The value can only be data, so it matches nothing.
  • Some drivers also run several statements in one call, and then the same flaw can delete a table.
  • That is why every query in this project uses a ? placeholder.

Experiment 4: opening the page straight from disk

With the server still running, double-click public/index.html so that the browser opens it from disk. The page stays on Loading.... Read the errors in the developer console.

What happened, and why
  • The console cannot load file:///app.js. The HTML says /app.js, and a leading slash means from the root of whatever served this page.
  • Served by our server, the root is the server. Opened from a file, the root is the top of your disk.
  • A page and its API need a server that delivers both.
  • On a project site such as GitHub Pages the root is a path like /project-name/, so a leading slash would point to the wrong place there, and a relative link such as app.js would work.

Experiment 5: the page on one port and the API on another

  1. Leave the API on port 8000. In a second terminal, serve only the public folder on port 9000, for example npx http-server public -p 9000.
  2. In the page's script, change the two URLs that begin with /api/ so that they begin with http://127.0.0.1:8000/api/. Run npm run build afterwards, because the browser runs the compiled file and not your TypeScript.
  3. Open http://127.0.0.1:9000.

The page says Cannot reach the server. Is it running?, yet the server is running. Check the console and the server's terminal before you read on.

What happened, and why
  • The console reports a CORS policy block. The server's terminal shows that it received the request and answered normally.
  • The browser delivered the request and then refused to let the script read the answer.
  • The reason is the same-origin policy. An origin is scheme, host and port together, and port 9000 is a different origin from port 8000.
  • By default a script may read responses only from its own origin. That stops a malicious page from reading your private data out of another site you are signed in to.
  • A server can opt in with a header. The policy it opts in to is CORS (Cross-Origin Resource Sharing).

To fix it, add one header to every response: "Access-Control-Allow-Origin": "http://127.0.0.1:9000" inside the object that sendBody passes to writeHead, next to the other headers. Restart the server and reload, and the page works.

  • Requests that carry a JSON body or custom headers trigger an extra preliminary OPTIONS request, which the server would also have to answer.
  • We named the exact origin and not *, which means any website. The wildcard suits public data and is risky when the response depends on who is asking.

Experiment 6: stopping the server

Press Ctrl+C to stop the server, return to the page and press Buy. Look at the status line and the console.

What happened, and why
  • The page shows Cannot reach the server. Is it running?, the same message as Experiment 5, though the cause is different.
  • fetch fails whenever no usable response arrives: the server is down, the network is off or the browser blocked the answer.
  • A 404 or a 409 still counts as an answer, and fetch does not treat it as a failure.
  • Think about how the script could give a more accurate message, and whether it can know enough to do so.

Experiment 7: changing data without touching any code

With the server running, change a price with UPDATE inventory SET price_cents = 99 WHERE slot_id = 'A1'; and reload the page.

What happened, and why
  • Sparkling Water now costs €0.99. Neither the server nor the page was edited or restarted.
  • The database is the single source of truth, and every request reads it again. That is why data lives in a database and logic lives in code.

Going deeperDesign choices and alternatives

Almost every line in this project was a choice, and most had a respectable alternative. For each choice the table gives the reason we chose as we did and the situation where you would choose differently. When you build your own project, ask yourself those same two questions about each decision.

The choiceWhy it fits hereWhen you might choose differently
SQLite for storageNothing to install, one file to copy, and the same SQL that bigger systems use.When many programs or computers write at once, or you need accounts, backups and monitoring at scale, a server database such as PostgreSQL fits better.
Node's built-in http module for the server, not a frameworkEvery mechanism stays visible: reading the request, routing and writing the response. Nothing needs installing.In real projects, because a framework such as Express, Fastify or Hono supplies routing, validation, safe static files and many conveniences. The next section describes what they add.
One database connection for the whole programNode runs our code on a single thread, so only one request touches the connection at a time, and the synchronous SQLite calls finish in microseconds. Sharing one connection also lets us prepare each statement once, at startup.With a client-server database, every call crosses a network and takes time, so the calls are asynchronous (they use await) and the program keeps a pool of connections.
The same server delivers the page and the APIBoth share one origin, so no CORS settings are needed, and only one program has to start.When the page lives on a static host such as GitHub Pages and the API lives elsewhere, the origins differ. The API then needs CORS headers and HTTPS.
JSON replies, with the page building its own elementsThe page and the API stay independent, and the same API can serve a phone app.When a page must work without scripts, the server can send finished HTML, and a form with a full page reload replaces the script.
Prices stored as whole centsWhole numbers are exact, so sums never drift.Some databases have an exact decimal type, which is also fine. A floating point column for money is never a good choice.
POST for buyingBuying changes data and is not idempotent, so a link preview must not be able to trigger it.Other changes use other methods: PUT to replace something, PATCH to adjust part of it, DELETE to remove it.
Parameterised queries everywhereThe database receives SQL and values separately, so a value can never turn into SQL.There is no good reason to choose differently.
One UPDATE with AND stock > 0A single statement checks and changes together. Reading first and writing afterwards leaves a gap in which two buyers could both take the last item.When a purchase needs several steps, group them in one explicit transaction, and think about what the database does when two transactions collide.
Rules in three placesThe page is a convenience, the server holds the rules and explains them, and the database is the last line of defence.You may drop the check in the page, because a visitor can skip it anyway. The server and database checks stay.
textContent rather than innerHTMLtextContent treats a value as plain text. innerHTML parses it as markup, so an item name containing a script tag could run code in every visitor's browser. That attack is cross-site scripting (XSS).innerHTML is fine for markup you wrote yourself and never for data from elsewhere.
A <template> element for the cardThe structure of a card stays in HTML, where it is easy to read and restyle, and not inside strings in the script.Front end frameworks such as React and Svelte generate this part for you and become worthwhile as pages grow.
Redrawing the card from the server's replyThe page shows what the server says, so it cannot drift from the truth. If somebody bought the last item a second ago, the reply says so.An optimistic update shows the change first and corrects it if the server disagrees. It feels faster on a slow network and costs more code.
A fixed list of files that the server will sendA server that sent whatever file the URL named could be asked for its own source code or the database file. That attack is path traversal.A framework's static file helper handles this safely, so use it instead of writing your own.

Why one UPDATE beats read-then-write

The diagram shows the race that a single UPDATE prevents. The same pattern of a check followed by a change appears in booking systems, bank transfers and ticket sales.

Where frameworks fit

  • Real projects rarely write server plumbing by hand. A framework provides routing, validation, safe static files, error handling and many conveniences.
  • We wrote the plumbing ourselves so that each mechanism is visible once.
  • The usual names in the Node world are Express (the oldest and most widely taught), Fastify (validation from a schema, built for speed) and Hono (small, runs on many platforms).
  • In each of them our route table shrinks to three lines such as on GET /api/slots, call this function, and the framework reads the request, sets the headers and sends the JSON.
  • All of them sit on the same node:http module that we used, so what you learned here is what they do underneath.

Going deeperExtend it yourself

Each extension below is small and practises one idea from this tutorial. They are problems to approach your own way, and the hints say where to start and no more.

  1. A restock route. Add POST /api/slots/A1/restock with a JSON body such as {"amount": 5}. Reject a missing body, invalid JSON and an amount that is not a whole number from 1 to 100, each with a 400. Node does not read the body for you. Collect the chunks with for await (const chunk of request), join them, and parse the text with JSON.parse. That loop needs await, so answerRequest becomes an async function.
  2. A sales log in the same transaction. Create a sales table with an id, a slot id that references inventory, a timestamp and the price paid. Make a purchase insert a sale and decrement the stock inside one transaction. Why should the sale store the price again? Then prove the transaction works: raise an error between the two statements and check that the stock did not change.
  3. A summary route. Add GET /api/sales/summary that returns, for each item, how many were sold and how much money they earned. This needs a JOIN and a GROUP BY, and the result has to arrive as clean JSON.
  4. Automatic refresh. Make the page ask for the slots every five seconds with setInterval, and open it in two windows. When you buy in one, how long until the other notices? Server-sent events and WebSockets let the server push changes instead.
  5. Separate hosting. Serve the page from its own port and make it work with CORS, as in Experiment 5. Then think about hosting only the page on GitHub Pages. You would need an absolute API address, a CORS header for your Pages origin, and an API reachable over HTTPS, because a page served over HTTPS may not call an insecure address.
  6. One type, shared. The Slot type is written twice, once in the server and once in the page script. Move it into a file that both can import, and discover what makes that harder than it sounds. Think about which program reads each import, and what a browser needs an import path to look like.

The agreed shape of requests and replies in an API: which fields exist and what type each has. (Step 3)

A program that stores data safely and answers queries about it, for example SQLite or PostgreSQL. (Step 2)

Document Object Model. The browser's live tree of objects, one for every element on the page. (Step 1)

One address of an API, such as /api/slots/A1. (Step 3)

A message that the browser creates when something happens on the page, such as a click. (Step 1)

Listening for events on a parent element instead of on each child, which also covers children added later. (Step 5)
fetch
The browser function that sends an HTTP request from a script and returns a promise. (Step 5)
Handler
The function that answers one kind of request. (Step 1)
Header
A name and value that describe a request or a response, such as Content-Type. (HTTP messages)
Host
The name or number that says which computer a request goes to. (Step 3)
HTTP
HyperText Transfer Protocol. The agreed text format of requests and responses between browsers and servers. (HTTP messages)
Idempotent
Describes an action that leaves the same result whether you do it once or many times. (HTTP messages)
JSON
JavaScript Object Notation. A text format for structured data, used by most web APIs. (Step 1)
Method
The word in a request that says what kind of action is wanted, such as GET or POST. (HTTP messages)
Origin
The combination of scheme, host and port. Pages may read responses only from their own origin unless the server allows more. (Break it on purpose)

A query in which values travel separately from the SQL text, marked by placeholders such as ?. (Break it on purpose)
Parsing
Turning text into a structure that a program can use, such as JSON text into an object. (Step 5)
Path
The part of a URL after the port, such as /api/slots. (Step 3)

An attack that uses parts such as /../ in a URL to reach files that were never meant to be served. (Design choices)
Port
A number that tells the operating system which waiting program should receive a message. (Step 3)
Primary key
A column whose value is different in every row, so it identifies exactly one row. (Step 2)
Promise
An object that stands for a value that has not arrived yet. (Step 1)
Protocol
An agreement about the order and shape of messages. (HTTP messages)
Relational database
A database that keeps its data in tables of rows and columns. (Step 2)
Request
A message from a client that says what it wants. (Step 1)
Response
The message a server sends back, made of a status code, headers and a body. (Step 1)
REST
Representational State Transfer. A style of web API in which URLs name things and methods choose the action. (HTTP messages)
Route
A pairing of a method and a path pattern with the function that handles it. (Step 1)
Safe method
A method that changes nothing on the server, such as GET. (HTTP messages)
Same-origin policy
The browser rule that stops a page from reading responses that come from another origin. (Break it on purpose)
Schema
The declared structure of a database: its tables, columns and types. (Step 2)
Serialising
Turning a structure in memory into text or bytes so that it can be stored or sent. (Step 5)
Server
A program that waits for requests and answers them. (Step 3)
SQL
Structured Query Language. The language for asking a relational database to find or change rows. (Step 1)

An attack in which text typed by a user becomes part of an SQL statement. (Break it on purpose)
Stateless
Describes a server that treats every request as new and remembers nothing between them. (HTTP messages)
Status code
The three digit number at the start of a response that says how the request went. (HTTP messages)
Transaction
A group of database steps that either all happen or none happen. (Step 1)
URL
Uniform Resource Locator. The address of something on the web, made of scheme, host, port and path. (Step 3)
Validation
Testing that input is well formed before using it. (Step 1)

Cross-site scripting. An attack that gets a page to run a script that arrived as data. (Design choices)
